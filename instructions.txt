# Nova_A 2.1.0 -> 3.0.0 Product and Engineering Roadmap

Document status: authoritative roadmap
Last reviewed: 2026-08-12
Product owner: Whitelist
Project: https://github.com/Stevenzhang543/Nova_A

## 1. Product decision

Nova_A is a professional, 2D-first game engine and editor. Its goal is not to copy every subsystem in Unity or Unreal Engine. Literal feature parity would require 3D rendering, ray tracing, VR/XR, cinematic virtual production, terrain, foliage, and AAA content pipelines, which would destroy Nova_A's lightweight identity.

The target is instead:

- Complete feature coverage for building, debugging, profiling, exporting, and extending serious 2D games.
- Familiar workflows for users coming from Unity, Unreal, Godot, GameMaker, or Defold.
- A small, fast core whose optional systems are loaded only when a project uses them.
- Precise world units and persistent Rust physics as first-class advantages.
- An open extension API so specialized capabilities do not have to become permanent core weight.
- Backward-compatible projects, explicit migrations, and no silent data loss.

Nova_A 3.0 must be better than broad engines in measurable, focused ways: editor startup time, empty-player size, iteration latency, deterministic 2D simulation, clarity of the 2D workflow, and the amount of functionality available without installing a large toolchain. It does not claim to be universally better at workloads outside its 2D scope.

## 2. What Nova_A already provides at 2.0.0

### Architecture and project data

- Vue 3 editor, Tauri desktop shell, WebAssembly bridge, and modular Rust workspace.
- Separate `nova_math`, `nova_physics`, `nova_runtime`, `nova_script`, `nova_format`, and `nova_wasm` crates.
- Persistent Rust physics world with stable runtime handles and a compact typed-array state bridge.
- Format 2 / schema 14 project documents, centralized validation and migration from older schemas.
- Project Manager, recent projects, autosave, templates, scenes, entities, components, hierarchy, parenting, UUIDs, prefabs, and overrides.
- Asset database with stable GUID references and import metadata.

### Runtime and gameplay

- Fixed-timestep runtime, time scale, pause, single-step, scene lifecycle, and collision/trigger events.
- Rhai scripting with lifecycle callbacks, input, entity, transform, physics, scene, audio, UI, save-data, and event APIs.
- Named keyboard, mouse, wheel, and gamepad input actions.
- Runtime UI components, event callbacks, focusable text input, and game-view interaction.
- Save slots and project-local runtime state.

### Physics

- Dynamic, kinematic, and static rigid bodies.
- Mass/density/inertia, forces, impulses, torque, gravity, damping, sleep, freeze rotation, and CCD settings.
- Convex polygon, ellipse, and editor shape collision with GJK/EPA/contact solving.
- Restitution, static/dynamic friction, sensors, one-way collision, physics layers, and masks.
- Fixed, distance, revolute, prismatic, and spring joints.
- Physical strings with bend/stretch constraints, collisions, anchor forces, and breakage.
- Rigid compound binding and separation.
- Layer isolation: objects on separate logical layers do not physically interact.
- Physics queries, diagnostics, collider overlays, contacts, and runtime statistics.

### Rendering and content

- WebGL2 renderer with Canvas2D fallback, batching, culling, editor overlays, ordering, cameras, sprites, shapes, and text.
- Texture import, tint, opacity, filtering, custom fonts, and layer-specific default colors.
- Sprite/property animation clips and animator controllers.
- Audio sources/listeners and audio buses.
- Particles and tilemaps.
- Editor Scene and Game views, move/rotate/scale gizmos, snapping, grids, axes, zoom, and selection.

### Production tools

- Assets, Console, Animation, Profiler, Tilemap, Project Settings, and Build Settings panels.
- Windows and web-oriented build/player pipeline, packed `.nova-pak` content, build reports, crash logs, and diagnostics.
- Initial sandboxed WASM plugin runtime.
- English, German, and Chinese UI and manuals.

## 3. Research comparison and lessons

The roadmap is based on official documentation reviewed in August 2026.

| Engine | Strongest workflow ideas | Expansion model | Trade-off Nova_A should avoid |
| --- | --- | --- | --- |
| Unity | Project/Hierarchy/Scene/Game/Inspector mental model; component composition; searchable Package Manager; UI Toolkit and visual authoring | Registry, Git, disk, and embedded packages; custom editor windows and inspectors | Large installation and many packages/subsystems visible even in small projects |
| Unreal Engine | Task-specific editors; World Outliner + Details; dockable layouts; Content Drawer stays hidden until needed | Code/data plugins, editor modes, utility widgets, menu/toolbar tools | 3D-first complexity and an intimidating number of specialized panels |
| Godot | Clear 2D/3D/Script workspaces; contextual docks; bottom panels folded by default; integrated docs and script editor | Editor/import plugins and GDExtension | A single inspector can still become long when nodes gain many capabilities |
| GameMaker | Multiple workspaces and pop-out layouts; direct room/object/sprite editors | Marketplace/extensions | Proprietary workflow and less general low-level control |
| Defold | Small editor; assets plus focused editors; compact runtime and reusable collections | Editor scripts and native extensions | Native extensions can require rebuilding a project-specific engine |

## 4. Feature gaps to close before 3.0

### Editor workflow gaps

- No task-focused workspaces or saved panel arrangements.
- No command palette or global command/search system.
- The inspector is a single long stream; adding components requires scrolling.
- No general dock/floating-panel model or user-named layouts.
- Asset types do not consistently open dedicated contextual editors.
- Limited keyboard-only navigation and editor accessibility.

### Scripting and gameplay gaps

- Script editor lacks language-service completion, symbol navigation, safe rename, breakpoints, watches, and a real debugger.
- Script modules, dependency declarations, coroutines/tasks, signals, and typed generated API documentation are incomplete.
- No optional visual scripting/state-graph gameplay system.
- Navigation, agents, behavior tools, and a production character controller are missing.
- Networking is missing; it should be optional rather than core weight.

### Rendering, animation, and content gaps

- No 2D lighting/shadows, normal maps, material graph, user shaders, render textures, camera stacks, or post-processing stack.
- Animation lacks curve editing, events, blend trees, skeletal rigs, IK, and a general timeline/sequencer.
- Asset importing lacks a dependency graph, content-addressed cache, background import workers, hot reimport, and platform variants.
- Tilemap workflow needs palettes, rule tiles, terrain painting, streaming chunks, and navigation/collision baking.

### Audio, UI, and world gaps

- No audio mixer effects, snapshots, ducking, streaming, or spatial attenuation authoring.
- UI needs responsive containers, style/theme resources, localization-aware layout, full focus navigation, and reusable UI scenes.
- No localization database, plural rules, fallback fonts, or translation preview.
- No world partition/chunk streaming or origin-management tools for large 2D worlds.

### Extensibility and shipping gaps

- Plugin API 1 is runtime-only and too small. It lacks editor commands, panels, importers, custom components, inspectors, settings, and build hooks.
- No package registry/client, dependency lockfile, compatibility resolver, signing, or permission review UI.
- Native desktop export is host-oriented; Android and polished platform templates are absent.
- Source-control status/diff/merge workflows and team-safe scene files need improvement.
- Automated scene/runtime tests, deterministic replay, memory budgets, and frame-trace capture are incomplete.

## 5. Non-negotiable engineering rules for every release

1. Preserve features and project data. When a workflow is replaced, the replacement must expose the same capability before the old UI is removed.
2. Never silently discard unknown components, fields, assets, plugin data, or newer project data.
3. Every persisted format change requires validation, migration, round-trip tests, corruption tests, and an explicit schema bump.
4. Every user-visible string must exist in English, German, and Chinese. Layout tests must include all three languages.
5. Physics uses finite `f64` values and exact world units. One configured metre equals one world metre; viewport zoom never changes simulation values.
6. Runtime physics remains in Rust. The frontend does not become a second authoritative physics implementation.
7. Rendering may interpolate visual transforms but must not write interpolated state back into physics.
8. Optional systems must be lazy or package-based. A project pays runtime and distribution cost only for features it uses.
9. No unbounded per-frame allocations, DOM growth, event listeners, timers, asset caches, logs, or script work queues.
10. Keyboard, mouse, gamepad, narrow-window, high-DPI, light/dark theme, reduced-motion, and all-language behavior must be audited.
11. Build gates are `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace --all-targets`, `vue-tsc --noEmit`, production web build, manual audit, and release-specific audits.
12. Each feature must have a visible UI entry, a saved representation when applicable, a runtime/calculation binding, error handling, undo/redo where applicable, documentation, and tests.

## 6. Performance and size budgets

These are release targets, not claims until measured on the documented reference machine.

- Editor cold start to usable Project Manager: <= 3 seconds.
- Existing-project open to editable scene for a medium project: <= 2 seconds excluding first-time external asset decoding.
- Empty standalone player executable and engine code: <= 15 MB before game assets and OS web-runtime prerequisites.
- Editor idle working set: <= 300 MB for an empty project.
- Inspector or workspace switch response: <= 100 ms at the 95th percentile.
- Script edit to hot-reload result: <= 500 ms for a small project.
- 10,000 visible static sprites at 60 FPS on the published integrated-GPU reference profile, with a documented benchmark scene.
- Physics produces no NaN/Infinity for any accepted finite input and remains stable across supported tick rates.
- A deterministic replay test produces identical checksums on repeated runs of the same engine build and platform.

Performance work may not reduce visual quality by silently lowering sampling, disabling animation, removing collision, or changing configured precision. Explicit quality levels are allowed only when user-selectable and documented.

## 7. Release plan

### 2.1.0 - Workspace and Editor UX Foundation

Goal: make every existing feature discoverable without making users search through one long right panel.

Implement:

1. Add a persistent workspace model with Design, Script, Animation, Interface, and Debug presets.
2. Add a workspace bar that switches page, hierarchy visibility, inspector visibility, bottom drawer tab, bottom drawer height, and focus mode as one reversible layout transaction.
3. Preserve the user's latest layout in local storage. Reject malformed stored values and provide Reset Layout.
4. Keep the bottom drawer collapsed in the default Design workspace. Never hide its tabs when it is available.
5. Add explicit Hierarchy, Inspector, Bottom Panel, and Focus Mode controls. Focus Mode is temporary and must not erase the saved layout.
6. Add a global command palette on `Ctrl/Cmd+K` and `Ctrl/Cmd+Shift+P`. Commands must be searchable by localized label and keywords, keyboard navigable, and usable without a mouse.
7. Include commands for workspaces, Scene/Game views, settings, every bottom tool, panel toggles, and layout reset.
8. Redesign the inspector header as a sticky control area with search, category filters, and an always-visible Add Component button.
9. Replace the bottom-of-inspector component list with a searchable, categorized component picker. This relocates the feature; it does not remove any component type.
10. Filter both core and optional/runtime components by category and translated name. A zero-result state must explain how to clear the filter.
11. Add responsive rules so the workspace bar, inspector picker, and command palette remain usable at the minimum 900 x 600 desktop size and in all three languages.
12. Update all version metadata to 2.1.0 and document the new navigation in all manuals.

Implementation boundaries:

- Workspace/layout state belongs in `src/editor`, not in physics or project documents.
- User layout preferences are machine-local and must never dirty or alter the game project.
- Existing editor page, bottom panel, inspector editing, undo/redo, and runtime-isolation behavior must remain unchanged.
- Workspace changes must call the existing resize/reconfigure path so the canvas never stretches or disappears.

Acceptance tests:

- Switch through every workspace and return to Design; no panel overlaps and viewport bounds remain valid.
- Reload the editor; layout preferences restore, while a corrupt preference falls back safely.
- Open every existing bottom panel through the command palette.
- Select an entity with every component; locate, edit, reset, copy/paste, and remove components with filters active.
- Add every allowed component without scrolling to the inspector bottom.
- Test keyboard-only palette/picker operation, Escape handling, three languages, both themes, high contrast, reduced motion, and 900 x 600.

### 2.2.0 - Script Studio and Gameplay Events

Goal: make scripting a first-class, debuggable workflow rather than a text field.

Implement:

- A dedicated Script workspace with tabbed files, project search, find/replace, line/column status, diagnostics, generated engine API reference, completion, signature help, hover documentation, symbol list, go-to definition, and safe rename.
- A parser/language service for the supported Rhai subset. Analysis runs in a worker and is cancellable.
- Compile-on-save and hot reload at a safe frame boundary. Keep previous valid bytecode if a new edit fails.
- Breakpoints, pause/continue/step, call stack, locals, watches, and bounded console inspection.
- Script modules, explicit exports, read-only project package dependencies, and circular-dependency diagnostics.
- Typed engine handles and consistent error values instead of silent null behavior.
- A signal/event system for editor-authored custom events, collision/trigger events, UI events, animation events, and scene lifecycle events.
- Coroutine/task primitives tied to scene/entity lifetime so destroyed owners cancel pending work.
- A script test runner with headless lifecycle, event, and error-isolation tests.

Do not allow script failures to crash physics, rendering, the editor, or unrelated entities. Debug-only facilities must be stripped from release players unless enabled.

### 2.3.0 - 2D Rendering, Materials, and Lighting

Goal: deliver modern 2D visuals while keeping the default renderer compact.

Implement:

- A render graph separating world, lighting, UI, editor overlays, and post-process passes.
- 2D point, spot, directional, and area lights; light layers/masks; ambient light; normal maps; shadow casters; soft-shadow quality levels.
- Material resources with shader, textures, uniforms, blend mode, sampling, and render-state data.
- A safe GLSL ES shader editor with compile diagnostics, preview, fallback material, and documented limits.
- Render textures, multiple cameras, camera stacks, viewport rectangles, pixel-perfect camera mode, and screenshots.
- Post-processing as optional passes: color adjustment, vignette, bloom, blur, and user shader pass.
- Nine-slice sprites, sprite atlases, texture compression/variants, and explicit sRGB/linear handling.
- GPU timing when supported, pass/batch/texture statistics, overdraw view, and render-debug captures.

Canvas2D remains a compatibility fallback. Projects that do not use lights or effects must not allocate their framebuffers or shader variants.

### 2.4.0 - Animation, Rigging, and Timeline

Goal: support character animation, procedural transitions, and scripted sequences.

Implement:

- A dedicated animation workspace with dope sheet, curve editor, key tangent modes, box selection, snapping, copy/paste, and multi-track editing.
- Animation events routed through the signal system.
- Animator blend trees, transition interruption, exit time, layers, masks, state-machine subgraphs, and live runtime preview.
- 2D skeletal rigs, bones, weighted sprite deformation, skin resources, IK chains, constraints, and pose tools.
- A general Timeline/Sequencer for animation, audio, camera, events, visibility, and script-call tracks.
- Recording of inspector/gizmo changes into keyframes with an explicit record mode.
- Animation import/reimport mapping and deterministic sampling independent of render FPS.

Old clips/controllers must migrate without visual changes. Timeline and rigging stay out of players that do not reference them.

### 2.5.0 - Asset Pipeline, Packages, and Plugin API 2

Goal: make large projects fast to iterate and make Nova_A safely extensible.

Implement:

- Content-addressed import cache keyed by source bytes, importer version, platform, and settings.
- Background import workers, progress/cancellation, atomic cache writes, file watching, debounced hot reimport, and failure fallback to the last valid artifact.
- Asset dependency/reverse-dependency graph, reference finder, unused-asset report, move/rename repair, missing-reference repair, and build inclusion explanation.
- Dedicated import settings and previews for images, atlases, fonts, audio, tile data, scripts, shaders, animations, and localization files.
- Package manifests, semantic-version resolution, lockfile, local/Git/registry sources, offline cache, update preview, compatibility report, and uninstall impact analysis.
- Plugin API 2 with versioned editor commands, menus, workspace panels, importers, asset editors, custom components, custom inspectors, gizmos, settings pages, build hooks, runtime systems, and events.
- Capability permissions, per-project enablement, signature/hash verification, time/memory limits for sandboxed extensions, crash isolation, and a Safe Mode startup.
- A package/plugin management UI that clearly separates installed, project, update, incompatible, and disabled packages.

Native extensions are optional advanced packages and must never be silently downloaded or executed. Standard plugins remain sandboxed WASM.

### 2.6.0 - Worlds, Navigation, and Gameplay Tools

Goal: make complete platformers, top-down games, simulations, and large 2D worlds practical.

Implement:

- CharacterBody2D/controller with slopes, steps, floor/wall/ceiling state, moving-platform velocity, one-way platforms, coyote-time helpers, and exact-unit motion APIs.
- Area2D/effectors for gravity zones, wind, drag, buoyancy, damage, and custom signals.
- Navigation regions, polygons, grid navigation, obstacles, agents, A*/flow-field options, avoidance, path smoothing, dynamic rebaking, and debug overlays.
- Behavior tree and hierarchical state-machine assets as optional gameplay tooling.
- Tile palettes, brush presets, rule/terrain tiles, layers, chunk streaming, collision/navigation/occluder baking, and large-map editing.
- World chunks, asynchronous scene streaming, portals, preload priorities, memory budgets, and origin shifting for large coordinates.
- Object pooling and spawn/despawn tools integrated with prefabs and lifecycle events.

Navigation and AI are separate runtime packages. A physics-only project must not carry them.

### 2.7.0 - UI, Audio, Localization, and Accessibility

Goal: support polished menus, HUDs, dialogue, audio mixes, and international releases.

Implement:

- Layout containers, anchors, size policies, safe areas, aspect constraints, responsive breakpoints, reusable UI scenes, clipping, masks, and scroll views.
- Theme/style resources with states, inheritance, variables, preview, and per-control overrides.
- Complete keyboard/gamepad focus navigation, focus visualization, screen-reader metadata export where the platform permits, and runtime input remapping widgets.
- Localization tables, locales, plural/select rules, variable formatting, fallback chains, pseudolocalization, font fallback, right-to-left layout, and live locale preview.
- Audio mixer graph with buses, sends, mute/solo, effects, meters, snapshots, ducking, spatial attenuation curves, streaming music, and voice limits.
- Audio waveform preview, loop markers, import normalization options, and profiler voice/buffer reporting.

Editor and runtime accessibility settings remain distinct. Localization data is stripped to selected build locales.

### 2.8.0 - Performance, Testing, Data, and Optional Networking

Goal: make correctness and scale repeatable rather than dependent on manual testing.

Implement:

- Frame trace recorder correlating input, scripts, animation, physics, audio, rendering, asset work, allocations, and GPU passes.
- Memory/asset budget tools, leak detection, object lifetime views, and capture comparison.
- Deterministic input recording/replay, physics checksums, fixed random seeds, and regression playback.
- Unit, scene, integration, and headless game tests with assertions, timeouts, screenshots, and CI-readable reports.
- Data resources, schema validation, generated typed accessors, database/CSV/JSON import, and migrations for save data.
- A bounded job/task scheduler with worker availability detection and a single-thread fallback.
- Optional networking package: transport abstraction, WebSocket and UDP-capable native transports, connection lifecycle, RPCs, replicated properties, snapshots, interpolation, prediction, rollback helpers, bandwidth limits, and multiplayer diagnostics.
- Authoritative-server/headless export mode and deterministic simulation tests for supported gameplay patterns.

Networking is disabled and excluded by default. Nova_A does not promise that arbitrary scripts or floating-point worlds are automatically deterministic across all hardware.

### 2.9.0 - Platform Export, Team Workflow, and Ecosystem

Goal: make shipping and collaborating reliable before the 3.0 stability promise.

Implement:

- Reproducible export templates for Windows, Linux, macOS, web, and an optional Android package where toolchain support is available.
- Platform presets, icons/splash, permissions, orientation, signing/notarization guidance, architecture selection, debug/release profiles, and validation before build.
- Incremental builds, build cache, package compression, patch/delta manifests, content hashes, deterministic build reports, and command-line/headless export.
- Player crash capture, symbol mapping workflow, structured logs, opt-in telemetry adapter, and privacy controls.
- Source-control status overlays, ignore-file generator, external diff/merge hooks, text-stable scene/prefab output, conflict detection, and safe lock files.
- Package registry client polish, publisher identity, permissions review, ratings/security links, and offline/local mirrors. No arbitrary extension executes during package browsing.
- Project upgrade preview, full backup option, compatibility analyzer, package audit, and rollback instructions.
- Example projects and templates exercising platformer, top-down, UI-heavy, physics-puzzle, and networked-optional workflows.

Console exports are not a 3.0 requirement because they require vendor programs and restricted SDKs. The public extension/build architecture must not block a future authorized backend.

### 3.0.0 - Nova_A Studio Stable

Goal: ship a stable, professional 2D engine whose full creation loop is coherent and supported.

Required end-to-end workflow:

Create project -> import assets -> build scenes/prefabs -> author input/scripts/animation/audio/UI -> run and debug -> profile/test -> save/load -> export -> launch a standalone player without editing engine source.

Release requirements:

1. Freeze and document the supported project schema, runtime API, Plugin API 2, package manifest, build CLI, and compatibility policy.
2. Provide automatic migration from every project format Nova_A has publicly shipped. Migration is previewable, backed up, atomic, and covered by golden files.
3. Run full audits of every component, property, button, selection, menu, shortcut, calculation, renderer binding, serialization path, localization, and manual anchor.
4. Publish benchmark methodology and measured results for startup, memory, build size, frame time, physics throughput, asset import, script reload, and export.
5. Meet the budgets in section 6 or publish the measured exception and corrective plan; never fabricate a passing result.
6. Run 24-hour stability tests, repeated play/stop cycles, scene streaming stress, asset reimport stress, corrupted-input fuzzing, and plugin fault isolation.
7. Verify Windows, Linux, macOS, web, and supported Android export on documented clean machines or CI runners.
8. Complete English, German, and Chinese UI/manual coverage, keyboard navigation, contrast, reduced motion, scalable UI, and minimum-resolution tests.
9. Ship reference games and source projects demonstrating platformer, top-down, UI, animation, audio, lighting, tilemap, save, plugin, and build workflows.
10. Publish clear known limitations: Nova_A remains a 2D engine and does not include built-in 3D, ray tracing, VR/XR, AAA terrain/foliage, cinematic virtual-production, or console SDKs.

The 3.0 core should include only the systems needed by most 2D games. Lighting, rigging, behavior tools, networking, Android support, and third-party integrations may be official optional packages. Removing an unused package must never make a project that does not reference it larger or slower.

## 8. Permanent release audit checklist

For every feature release, the coder must produce an edit ledger and answer all of these with evidence:

### UI and interaction

- Does every visible control execute a real command or update a real persisted/runtime property?
- Is disabled state accurate and explained where necessary?
- Are focus, hover, pressed, selected, validation, loading, empty, error, and success states visible?
- Does it work with mouse, keyboard, trackpad/wheel, and at minimum window size?
- Does it work in English, German, and Chinese, light/dark themes, high contrast, and reduced motion?
- Are dialogs inside the Nova_A UI rather than native browser confirm/prompt windows?

### Data and history

- Does save/load round-trip the feature without numeric or reference drift?
- Does undo/redo include it and coalesce continuous edits correctly?
- Are old projects migrated and unknown/newer fields preserved or rejected safely?
- Do duplicate, prefab, scene switch, play/stop isolation, build, and import/export paths preserve it?

### Runtime and calculations

- Is the editor property connected to the authoritative runtime/calculation path?
- Are units, clamping, finite-value validation, defaults, and edge cases documented and tested?
- Does renderer output match runtime state without one-frame stale data or scale conversion errors?
- Are different render/physics layers handled deliberately?
- Are allocation, cache, event-listener, and destruction lifetimes bounded?

### Verification

- Rust format, clippy, tests, TypeScript check, production build, manual audit, and release audit pass.
- Browser smoke tests cover Project Manager, Scene, Game, Settings, all workspaces, all bottom panels, inspector filters/picker, save/load, play/stop, and representative build settings.
- The edit ledger lists every file added, modified, deleted, and mechanically regenerated, with functional consequences and known limitations.

## 9. Versioning policy

- `x.0.0` is a major compatibility or product-identity release.
- `x.y.0` is a planned feature release.
- `x.y.z` is a bug-fix or contained feature-adjustment release.
- Project schema, package API, and plugin API versions are independent from application SemVer. They change only when their data/contracts change.
- A version number is updated only after implementation and release checks pass; development builds may display a prerelease suffix.
