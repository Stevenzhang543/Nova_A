# Historical Nova_A 5.1.0–6.1.0 production roadmap

Product direction: a lightweight, fast, local-first 2D game engine and editor with the essential production capabilities of Godot, GameMaker, Unity and Unreal, without their 3D-first weight, mandatory online services, or duplicated expert-only workflows.

## 1. Rules for every release

1. Preserve user-authored project data, animations, scripts, graphics, shortcuts and interaction paths. Replacements must migrate losslessly and remain undoable where applicable.
2. A panel or data type is not a completed feature. Completion requires connected authoring, persistence, runtime behavior, diagnostics, documentation and automated verification.
3. Keep Project Format 2/schema 29, Rhai API v2, Plugin API 2, Package Manifest 1, Build CLI 1 and workspace document 3 compatible throughout 5.x. Additive fields use safe defaults; incompatible changes wait for 6.0 with migration.
4. Every feature receives four audits:
   - Programmer: types, finite-value validation, error boundaries, determinism, lifecycle, serialization and tests.
   - Runtime: the authored value reaches the player and produces observable behavior.
   - User: a first-time user can find, understand, use, undo and troubleshoot it.
   - Layout: English, German and Chinese at 1024×640, 1366×768, 1920×1080, 2560×1440 and high DPI, with no overlap, clipping, hidden browser-style scroll strip or unreadable text.
5. Every version ships the exact eleven release files: portable Windows executable, MSI, setup executable, web archive, source archive, reference-project archive, evidence archive, release notes, edit ledger, license and SHA-256 manifest.
6. Network access, telemetry, publishing, signing and external tools remain explicit. Failed checks fail closed and explain the remedy.
7. Prefer one discoverable workflow over several partial panels. Advanced controls use progressive disclosure, search and context help.

## 3. Competitive gap analysis

### Already competitive

- Action input, lifecycle, collision callbacks, signals, timers, prefabs, saves and scenes cover core 2D arcade, puzzle, platformer and top-down loops.
- Deterministic project text, transactional recovery, local-first collaboration and release evidence are unusually strong for a lightweight editor.
- The 2D physics/rope workflow, responsive multilingual UI auditing and build provenance are broader than many small 2D tools.
- A project can currently become a web player, desktop player plus pack, or single-file Windows/Linux player on a matching host.

### Important gaps versus Godot, GameMaker, Unity and Unreal

1. Visual programming: Nova_A has only text Rhai. It needs an event/data/control graph generated from the same authoritative API, not a separate weaker runtime.
2. Dynamic object API: advanced games need spawn transforms and stable returned handles, targeted entity/component/UI mutation, enable/disable and structured queries.
3. Input expressiveness: add action contexts/maps, schemes, hold/tap/multi-tap phases, consumption/priority and event callbacks.
4. Gameplay framework: add coherent controllers, state/behavior assets, abilities, damage, collectibles, projectiles, dialogue and game flow.
5. Extension depth: third parties cannot yet add every dock, Inspector, importer, renderer pass, graph node, build target and native module as smoothly as mature engines.
6. Content depth: animation, shaders, particles, audio and TileMaps need graph authoring, preview ergonomics, richer blending/sequencing and import interoperability.
7. Platform reach: mature engines cover more desktop/mobile/console/XR. Nova_A should qualify desktop/web/mobile selectively; consoles/XR/3D stay out unless a real need exists.
8. Ecosystem: the registry model lacks a mature public catalog, publisher workflow and broad third-party library.
9. Learning: current docs describe panels, but do not systematically teach end-to-end tasks, choices and recovery.
10. Production proof: external hardware/browser, long-soak, signed-build and independent clean-machine evidence remains pending.

## 4. Product layout target

- Six task workspaces: Design, Script, Animation, Interface, Debug and Manage.
- Left: project/scene/assets. Center: primary editor. Right: contextual Inspector. Bottom: task-specific secondary tools.
- Never put unrelated systems in one long Inspector. Selection data belongs in Inspector, project-wide settings in Manage, runtime evidence in Debug.
- Complex editors use a consistent catalog / canvas / details layout, collapsing into tabs below 1180 px.
- Direct actions remain visible; infrequent settings use named groups. Search and Command Palette access are mandatory.
- Motion communicates entry, selection, execution and validation and honors reduced motion.
