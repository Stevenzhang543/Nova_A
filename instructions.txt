
# Nova_A 4.0.0 Capability Audit, UI Modernization Specification, Full Verification Program, and Development Roadmap

## Version 4.1.0 through Version 5.0.0

**Document ID:** NOVA-A-PLAN-4.1-5.0  
**Status:** Engineering Planning Baseline — not a functional certification  
**Prepared for:** Code Department  
**Prepared by:** Chief Development Planner  
**Date:** 20 August 2026  
**Product reviewed:** Nova_A 4.0.0, Nova_A Project Format 2, visible schema 29  
**Evidence supplied:** Thirteen screenshots covering the launcher and principal editor workspaces

## Document Purpose

This document converts the supplied Nova_A 4.0.0 screenshots into an engineering plan. It has five purposes:

1. Identify the functions that are visibly present in Nova_A 4.0.0.
2. Separate directly observed capability from functionality that is only implied by labels, tabs, template descriptions, or status cards.
3. Identify the remaining gaps between Nova_A and a mature, stable, developer-friendly 2D engine.
4. specify which visible features should be retained, moved, merged, hidden, renamed, redesigned, or removed from the primary workflow.
5. Define a release-by-release development, testing, and release-evidence plan from 4.1.0 through 5.0.0.

A screenshot proves that an interface exists. It does not prove that the underlying operation is correct, deterministic, safe under failure, compatible with older projects, performant at scale, or suitable for production. Therefore, this document includes a complete verification program, but it does **not** claim that Nova_A 4.0.0 has already passed those tests. Executing the verification program requires the runnable editor, exported players, source code or test hooks, representative projects, and build infrastructure.

# 1. Executive Assessment

## 1.1 Overall conclusion

Nova_A 4.0.0 presents a much more credible editor product than a collection of disconnected prototype panels. The supplied screenshots show a coherent project launcher, a multi-workspace editor, integrated scene authoring, a Rhai Script Studio, animation tooling, a responsive UI workspace, a deterministic-looking asset importer, a package manager, a frame profiler, live physics telemetry, an audio mixer, rendering capability inspection, project-health diagnostics, and a structured build surface.

The strongest change is not simply that more features are visible. The editor now communicates a clearer product architecture: authoring workspaces at the top, contextual side panels, a reusable bottom dock, a project-health concept, and a build-readiness concept. The asset importer exposes GUID and SHA-256 information; the physics template demonstrates live object telemetry; the script editor exposes test and debugger controls; and the build page distinguishes platform, delivery, history, and team concerns.

However, Nova_A 4.0.0 still cannot be classified as a mature production engine from screenshots alone. The screenshots do not prove complete undo and redo coverage, atomic saves, crash recovery, migration safety, dependency-preserving asset operations, prefab override integrity, debugger correctness, deterministic export, clean-machine installation, package signature verification, cross-platform output, long-duration stability, or automated regression coverage. Several advanced systems are represented by tabs or buttons without enough evidence to establish depth.

The appropriate product classification is therefore:

> **An integrated beta-stage 2D engine editor with promising production-oriented tooling, but without sufficient evidence for production certification.**

The 4.1.0–5.0.0 program should prioritize workflow integrity, data safety, automation, interface clarity, and platform reliability over adding more top-level feature categories.

## 1.2 Most convincing visible strengths

- A professional launcher with project templates, recent projects, migration language, a manual entry point, language selection, and clear editor/player separation.
- A consistent editor shell with Design, Script, Animation, UI, and Debug workspaces.
- A 2D scene viewport with hierarchy, scene list, layers, transform modes, snapping, camera framing, HUD canvas boundaries, and object creation controls.
- A significantly improved Rhai Script Studio with exported-property metadata, lifecycle callbacks, diagnostics, symbols, modules, tests, API browsing, navigation, formatting, references, and debugger controls.
- A detailed animation surface with dope sheet, curve editor, recording, snapping, frame rate, playback speed, looping, onion skin, events, markers, method tracks, audio tracks, nested animation, rigs, skins, masks, timelines, and animator-controller entry points.
- A dedicated responsive-UI surface with canvas creation, anchors, containers, breakpoints, safe-area preview, DPI preview, RTL preview, themes, reusable UI scenes, localization, accessibility, focusable-control counts, and UI audio references.
- An asset browser and importer that exposes project paths, stable GUIDs, import caching, source hashes, artifact hashes, unused-resource reporting, and missing-reference reporting.
- A package manager with offline mode, compatibility states, lockfile awareness, manifest import, safe mode, and a declared stable plugin contract.
- An integrated profiler with subsystem frame timing, memory, GPU passes, object counts, job counts, physics diagnostics, replay, tests, data, jobs, scripts, and debug categories.
- A live Physics Monitor with object properties, collision timeline, per-body motion values, force, kinetic energy, contacts, state, layer, pause, and simulation-step count.
- An audio mixer with buses, snapshots, live mix, voice limits, sends/effects entry points, waveform and loop-marker surface, streaming statistics, latency, underrun, and device-change counters.
- A rendering workspace that exposes lighting, materials, shaders, particles, diagnostics, quality, ambient light, shadow quality, capability tier, backend, texture size, normal-map support, and context recovery.
- A Project Health workspace that summarizes project format, schema, engine compatibility, manifest, scenes, assets, packages, build settings, renderer backend, world size, tile counts, navigation, and streaming memory.
- A structured build interface with presets, target, architecture, build profile, runtime mode, output path, content packaging, readiness status, cache information, Build, and Build & Run.

## 1.3 Highest-risk remaining gaps

- **No proof of project safety:** atomic writes, journal recovery, autosave restoration, cross-file transactions, corruption repair, and full undo/redo are not demonstrated.
- **No proof of large-project integrity:** rename-safe references, dependency graphs, circular-reference handling, prefab overrides, scene inheritance, and bulk asset operations are not demonstrated.
- **No proof of complete editor ergonomics:** the interface still contains duplicate navigation, overloaded bottom tabs, persistent unrelated diagnostics, dense card layouts, inconsistent selected states, and mixed typography.
- **No proof of debugger depth:** debugger controls are visible, but breakpoints, conditional breakpoints, call stacks, locals, watches, evaluation, remote debugging, and hot-reload rules are not shown.
- **No proof of animation depth:** many animation entry points are visible, but state-machine behavior, blend trees, curve tangents, key editing, retargeting, skeletal constraints, compression, and runtime determinism are not shown.
- **No proof of runtime UI depth:** responsive concepts are visible, but authoring behavior, reusable-component overrides, style inheritance, input modality, localization extraction, accessibility tree output, and runtime compatibility are not shown.
- **No proof of renderer breadth:** the visible project uses WebGL2 Tier 1. Native renderer architecture, shader portability, batching, texture compression, post-processing, render targets, context-loss handling, and GPU compatibility remain uncertain.
- **No proof of audio completeness:** mixer concepts are visible, but real effects, 2D spatial audio, streaming robustness, decoding, resampling quality, device recovery, and export behavior are not shown.
- **No proof of build reproducibility or platform depth:** the visible build target is Windows x86-64 on the host. Linux, macOS, web deployment validation, mobile, command-line export, signing hooks, CI, clean-machine tests, and deterministic output are not demonstrated.
- **No proof that every visible control works:** a complete control inventory and automated end-to-end test suite are required before 5.0.0.

## 1.4 Product definition for Nova_A 5.0.0

Nova_A 5.0.0 should be declared production-stable only when all of the following are true:

- The project format is deterministic, documented, migration-safe, source-control-friendly, and recoverable after interruption.
- Every editor mutation that changes project state participates in undo/redo and atomic save transactions.
- Scenes, entities, components, prefabs, assets, scripts, animations, UI resources, and build presets maintain stable references during rename, move, duplication, import, reimport, and migration.
- The editor has a consistent, accessible, high-DPI-safe visual system with no uncontrolled font mixing or raster-scaled text.
- The Script Studio has production-grade diagnostics, navigation, refactoring, debugging, hot reload, testing, and a versioned public API.
- The 2D authoring pipeline covers sprites, atlases, TileMap2D, cameras, paths, parallax, particles, materials, lighting, fonts, and UI without requiring manual file editing.
- Physics, animation, audio, rendering, input, localization, accessibility, save data, and navigation have documented runtime behavior and regression suites.
- At least Windows and web are Tier-1 export targets; additional platforms have explicit Tier-2 or Experimental labels.
- Packages use semantic versioning, lockfiles, signatures or trusted provenance, permissions, safe mode, compatibility checks, and rollback.
- Every release is reproducible, installable on clean machines, covered by automated tests, accompanied by evidence, and free from unresolved severity-0 or severity-1 defects.

## 1.5 Planning priorities

1. **P0 — Preserve work and references.** Project safety, undo/redo, recovery, migration, dependency integrity, and deterministic serialization.
2. **P0 — Make the editor understandable.** Information architecture, typography, docking, global search, selected states, keyboard operation, and high-DPI rendering.
3. **P0 — Make behavior verifiable.** Control inventory, headless test execution, end-to-end automation, evidence capture, and release gates.
4. **P1 — Deepen core 2D workflows.** Scene/prefab, assets, scripting, physics, animation, UI, TileMap2D, rendering, and audio.
5. **P1 — Make shipping reliable.** Platform exports, deterministic builds, installers, package safety, documentation, and support policy.
6. **P2 — Add breadth only after integration.** New advanced systems must not become primary navigation until they have complete authoring, runtime, serialization, documentation, and tests.

# 2. Review Method, Evidence Limits, and Benchmark

## 2.1 Evidence basis

This assessment uses thirteen screenshots of Nova_A 4.0.0:

- S1 — Project Launcher and Project Templates.
- S2 — Design Workspace and 2D Scene Editor.
- S3 — Script Studio.
- S4 — Animation Workspace.

- S8 — Package Manager and Extension Safety.
- S9 — Console and Physics Monitor.
- S10 — Audio Mixer and Physics Monitor.
- S11 — Rendering Workspace and Capability Summary.
- S12 — Project Health.
- S13 — Build Settings.

No executable, source tree, project archive, automated test report, profiler capture, package manifest, migration log, installer log, or exported game was supplied. Therefore, all stability and correctness statements in this document are requirements, not confirmed results.

## 2.2 Confidence labels

- **Observed:** directly visible in a screenshot.
- **Implied:** a label, button, tab, template description, counter, or status strongly suggests the function, but the complete workflow is not visible.
- **Not evidenced:** the supplied screenshots do not establish that the capability exists or works.

## 2.3 Competitive benchmark

The benchmark is based on categories documented by mature engines, not on copying another editor. Godot's current stable documentation describes a scene-tree editor, built-in script editor, debugger, CPU/GPU profiling, live editing, remote inspection, embedded game execution, plugins, dedicated 2D rendering and physics, TileMaps, animation, GUI, input, audio, navigation, command-line automation, and export workflows. GameMaker's current manual documents deep asset-specific editors, object/instance workflows, room editing, code intelligence, debugger and profiler tools, sequences with dope-sheet editing, particle authoring, and extensive asset tooling.

Nova_A does not need identical terminology or every competing feature. It does need comparable end-to-end completeness: authoring, serialization, debugging, automation, documentation, failure recovery, and release validation.

# 5. Maturity Gap Analysis

## 5.1 Editor information architecture and workspace model

### Current evidence and concern

Nova_A 4.0.0 has a recognizable workspace model, but the same concepts are exposed through top workspaces, a left rail, and a large bottom-tab strip. Debugging functions appear both as a top Debug workspace and as bottom Profiler/Console panels. Animation and UI are both top-level workspaces and bottom-panel concepts. Packages, Rendering, Project Health, and Build Settings occupy the same bottom strip as transient tools such as Console and Assets.

### Required capabilities

- A single authoritative navigation model with no competing route to the same context.
- A distinction between primary workspaces, contextual docks, transient tools, and project-management pages.

# 6. User-Experience Audit and UI Modernization Specification

## 6.1 Functions and design choices that should be retained

The following visible decisions are valuable and should remain part of Nova_A's identity:

- **Template-led project creation.** The launcher communicates practical use cases rather than exposing an empty directory chooser first.
- **Editor/player separation.** This is a strong product and security boundary and should remain explicit.
- **Workspace-oriented editing.** Design, Script, Animation, UI, and Debug are understandable user intents.
- **Integrated project health.** A single place that summarizes references, packages, renderer capability, build readiness, and project scale is highly valuable.
- **Stable identity and import evidence.** GUIDs, source hashes, artifact hashes, and import-cache status are excellent foundations for deterministic content handling.
- **Embedded play and diagnostics.** Running the game inside the editor while using Console, Profiler, Physics Monitor, and debugging tools is developer-friendly.
- **Live physics telemetry.** The physics template demonstrates an unusually strong debugging concept; it should be improved rather than removed.
- **Rhai metadata annotations.** Export annotations with type, range, grouping, and tooltip information can make scripts designer-friendly.
- **Responsive UI preview.** DPI, safe-area, RTL, focus, reusable UI scenes, themes, localization, and accessibility are the correct categories.
- **Structured build workflow.** Presets, platform, delivery, diagnostics/history, and team are better than one opaque export button.
- **Package safe mode and lockfile concepts.** These are appropriate for a production tool that executes third-party code.
- **Status and task-center concepts.** The editor needs persistent but unobtrusive feedback for background import, build, test, and migration work.

## 6.2 Features that should be removed from the primary interface, merged, or relocated

“Remove” in this section usually means remove from the default primary surface, not delete the underlying capability.

### 6.2.1 Duplicate navigation routes

The top workspace row, left rail, and bottom tab strip expose overlapping concepts. The left **Game** destination overlaps with the top **Debug** workspace. **Animation** exists as both a top workspace and a bottom panel. **UI** and the in-page **Presentation** label overlap. This increases cognitive load and makes the current location unclear.

**Required action:** use one top-level workspace model. The left rail should show contextual tools within the current workspace, not a second global navigation system.

### 6.2.2 Permanent Physics Monitor in unrelated work

The Physics Monitor remains open while the user views Audio mixer, Rendering, Project Health, and Build Settings. This consumes substantial horizontal space and implies that physics is globally important even when the current task is unrelated.

**Required action:** make Physics Monitor a dockable Debug tool that opens automatically only when requested, when a physics object is selected, or when a captured physics issue is activated.

### 6.2.3 Project-management pages inside the transient bottom dock

Packages, Rendering, Project Health, and Build Settings require full-page information architecture, not the same constrained height used for Console or Assets. Their current placement creates nested scrolling and forces the user to interpret major workflows in a short horizontal strip.

**Required action:** move Packages, Project Health, Build Settings, and global Renderer settings to a dedicated **Manage** workspace. Keep Console, Problems, Assets, Timeline, Profiler capture, and other transient tools in the bottom dock.

### 6.2.4 Internal terminology as user-facing actions

**Stable plugin contract**, **Complete**, **Tier 1**, and several abbreviated labels are implementation-oriented or ambiguous. They do not describe the user's action or outcome.

**Required action:** rename to outcome-oriented language, for example:

- Stable plugin contract → **Plugin API compatibility**
- Complete → **Code completion** or remove the button and provide completion automatically
- Tier 1 → **Compatibility renderer — supported feature set** with a details link
- Manage → **Project tools** unless it truly opens a broad management workspace

### 6.2.5 Template-specific instructional text inside the general editor shell

“Press Play, then inspect live collision, joint, and Rope2D telemetry” is useful in the Physics Sandbox reference project, but it should be scene content or an onboarding callout rather than persistent editor chrome.

**Required action:** move template instructions into dismissible project tutorials stored with the reference project.

### 6.2.6 Card-heavy presentation for data-dense diagnostics

Project Health and Physics Monitor use large cards for information that developers compare row by row. Cards consume space, make scanning slower, and force excessive scrolling.

**Required action:** use virtualized tables with sortable columns, filtering, grouping, pinning, and a detail pane. Reserve cards for summaries and empty states.

### 6.2.7 Primary toolbar actions with low frequency

**Export folder** is presented beside daily asset actions even though folder export is not a common operation. Technical hash metadata is always visible even when a designer only needs import status.

**Required action:** move low-frequency operations to context menus or an overflow menu. Show hashes in an expandable **Provenance** section with copy buttons.

### 6.2.8 Ambiguous icon-only transform and creation tools

Several icons are difficult to identify, and small letter hints appear to compete with the icon itself. This design favors users who already know the tool and penalizes new users.

**Required action:** use consistent vector icons, persistent tooltips, a visible tool name in the status bar, shortcut hints in tooltips, and an optional labeled toolbar in the Beginner workspace profile.

### 6.2.9 Contradictory readiness states

Build Settings says **Ready to build** while simultaneously warning that no explicit content-inclusion rule is configured. This weakens confidence in all future readiness messages.

**Required action:** define four states: Blocked, Ready with warnings, Ready, and Building. A warning cannot be visually equivalent to a fully ready state.

### 6.2.10 Red volume sliders without an error condition

The audio sliders use red while the rest of the editor uses blue. Red normally communicates clipping, danger, or failure.

**Required action:** use the normal accent for control position. Use green/amber/red only in level meters when signal levels cross documented thresholds.

### 6.2.11 Redundant Manual entry

The launcher includes a Manual button while the editor has a Help menu. Two routes are not harmful, but the launcher button consumes premium space and does not indicate whether the manual is offline, version-matched, or contextual.

**Required action:** keep a first-launch **Learn** action and retain the Help menu. The launcher button should become **Learn Nova_A** and open version-matched onboarding, examples, and the manual.

## 6.3 Layout and visual problems that affect real development

### 6.3.1 Too many horizontal navigation rows

The editor can show the application menu, workspace row, workspace-specific toolbar, bottom-tab row, bottom-panel toolbar, and status bar at the same time. On a 1080p display, this removes a large percentage of vertical authoring space.

**Correction:** consolidate controls into a two-level model: application/workspace header and one contextual toolbar. The bottom panel should have a single tab row and appear only when open.

### 6.3.2 Unbalanced center, left, right, and bottom regions

When no object is selected, the Inspector remains wide and nearly empty. When Physics Monitor is open, it remains wide even in unrelated tools. The center viewport can therefore become smaller than necessary.

**Correction:** auto-collapse empty context docks, remember user width, enforce useful minimum and maximum widths, and allow a one-key Focus Mode that truly dedicates the screen to the current task.

### 6.3.3 Weak selected, focused, hovered, and disabled-state differentiation

Multiple blue treatments are used for selected tabs, selected cards, and focus states. Disabled buttons are sometimes only slightly dimmer than enabled controls. In the launcher, multiple template cards can appear visually emphasized.

**Correction:** define independent tokens for selection, keyboard focus, hover, active press, drag target, warning, and disabled state. Only one project template may use the selected treatment.

### 6.3.4 Dense text at inconsistent sizes

Some section headings are large and bold while important field labels are very small. Similar controls use different apparent sizes and weights. Long lines in Script Studio and diagnostic cards have insufficient visual hierarchy.

**Correction:** adopt the typography system in Section 6.6 and prohibit ad hoc font size, weight, and line-height values outside design tokens.

### 6.3.5 Too much nested scrolling

UI, Assets, Audio, Rendering, Project Health, Build Settings, and Physics Monitor can each contain independent scroll regions. Nested scroll regions cause accidental scrolling in the wrong panel and reduce trackpad usability.

**Correction:** give major pages one primary scroll container. Use sticky headers, virtualized tables, and resizable split panes instead of stacked nested scrollboxes.

### 6.3.6 Weak action hierarchy

Primary, secondary, neutral, and destructive actions do not always have a consistent appearance. Build and Build & Run are differentiated, but many other screens use similarly styled buttons for creation, navigation, configuration, and diagnostics.

**Correction:** define action hierarchy:

- Primary: one per view or task step.
- Secondary: supporting actions.
- Tertiary/ghost: navigation and low-risk utilities.
- Destructive: red only when the action can remove or irreversibly alter data.
- Toggle: visibly represents state and never resembles a momentary command.

### 6.3.7 Insufficient visible causality

A developer needs to know what changed, whether it was saved, whether a background import is running, why a control is disabled, and what task caused a warning. Current status surfaces are present but not visibly connected to affected resources.

**Correction:** every disabled control must expose a reason; every background task must expose source, progress, cancellation state, log, and affected resource; every warning must link to a fix location.

## 6.4 Proposed 5.0 information architecture

### 6.4.1 Primary workspaces

1. **Design** — scenes, hierarchy, inspector, 2D viewport, sprites, TileMap2D, cameras, paths, physics authoring.
2. **Script** — Rhai editing, API browser, tests, debugger, coverage, external-editor integration.
3. **Animation** — clips, curves, events, state machines, rigs, skins, masks, timelines.
4. **UI** — runtime UI canvas, responsive layout, themes, localization, accessibility, UI audio references.
5. **Debug** — embedded runtime, remote scene tree, Console, Profiler, Physics Monitor, replay, data, jobs, memory.
6. **Manage** — project settings, packages, Project Health, rendering/quality policies, input map, build/export, team, diagnostics history.

The user may hide workspaces that are not relevant to the project. Experimental workspaces must be opt-in and cannot occupy default navigation.

### 6.4.2 Dock roles

- **Left dock:** scene/resource navigation for the current workspace.
- **Center:** primary editor or runtime viewport.
- **Right dock:** Inspector or context-specific detail; one principal context at a time.
- **Bottom dock:** transient tools such as Assets, Console, Problems, Timeline, Profiler capture, Search results, Tests, and Task log.
- **Floating/folded tools:** Physics Monitor, API documentation, comparison views, and diagnostics details.

### 6.4.3 Global navigation and search

- `Ctrl+Shift+P`: command palette.
- `Ctrl+P`: quick-open scene, asset, script, setting, symbol, test, or build preset.
- `Ctrl+K`: context search within the active editor.
- Search results must show type, path, owning scene, reference count, and actionable context.
- Commands must be searchable by both user-facing name and legacy/internal alias during migration.

### 6.4.4 Workspace profiles

Provide at least:

- **Beginner:** labeled tools, fewer docks, contextual help, larger controls.
- **Designer:** hierarchy, viewport, inspector, assets, timeline.
- **Programmer:** script tree, editor, problems, tests, API, debugger.
- **UI designer:** hierarchy, UI canvas, responsive preview, theme/localization panels.
- **Profiler:** embedded runtime, frame trace, memory, scripts, physics, GPU, console.
- **Release engineer:** Project Health, build presets, package lock, diagnostics history, evidence generation.

Profiles are starting points, not separate products. Changes are saved per user and may be reset without touching the project.

## 6.5 Design-token and component specification

### 6.5.1 Spacing and sizing

Use a 4-pixel base grid:

| Token | Value | Typical use |
|---|---:|---|
| Space-1 | 4 px | Icon/text gap, compact internal spacing |
| Space-2 | 8 px | Standard control gap |
| Space-3 | 12 px | Compact panel padding |
| Space-4 | 16 px | Standard panel padding |
| Space-6 | 24 px | Section separation |
| Space-8 | 32 px | Major page separation |

Control heights:

- Compact: 28 px.
- Default: 32 px.
- Comfortable: 36 px.
- Launcher primary action: 40 px.
- Do not create one-off heights unless a component specification requires it.

Panel minimums:

- Left tree: 220 px.
- Inspector/detail: 280 px.
- Bottom panel: 180 px closed-to-open minimum, user resizable.
- Center viewport minimum: 480×320 logical pixels before panels auto-collapse.

### 6.5.2 Border radius and elevation

- Small controls: 6 px.
- Inputs and standard buttons: 7 px.
- Cards, popovers, and panels: 9 px.
- Modal/dialog: 10 px.
- Avoid excessive nested rounded rectangles; use dividers and grouping when data is dense.
- Shadows are reserved for floating surfaces, not every panel.

### 6.5.3 Color semantics

- Blue accent: selection and primary action.
- Neutral gray: inactive controls and structure.
- Green: successful completed state only.
- Amber: warning or degraded state.
- Red: destructive action, error, clipping, or failed validation only.
- Purple or teal may be used for data-series differentiation, not arbitrary decoration.
- All text/background combinations must meet WCAG AA contrast at the intended size; critical status indicators must not depend on color alone.

### 6.5.4 Iconography

- One vector icon set, 16 px and 20 px optical sizes.
- Consistent 1.5–2 px stroke weight, corner treatment, and filled/outline policy.
- Every icon-only action must have an accessible name and tooltip.
- State icons must be paired with text or shape changes where meaning is critical.
- Avoid using letters inside icons as the primary explanation of transform tools.

### 6.5.5 Tables and diagnostic data

- Use virtualized tables for more than approximately 100 rows.
- Support column resize, sort, filter, pin, copy, and export.
- Keep units in headers or dedicated unit columns.
- Display high-frequency values in aligned tabular numerals.
- Use a details pane for full vectors, hashes, stack traces, and provenance.
- Preserve selected row and scroll position when data refreshes.

### 6.5.6 Notifications and task handling

- Toasts: transient success or low-risk information only.
- Inline banner: issue affecting the current view.
- Task center: imports, builds, migrations, tests, package operations, and long-running analysis.
- Modal dialog: only when user input is required before work can safely continue.
- Every failed task must preserve logs and provide Retry, Open details, and Copy diagnostic summary.

## 6.6 Typography and text-rendering standard

### 6.6.1 Recommended primary UI typeface

**Primary UI typeface: Nunito Sans Variable.**

Nunito Sans is recommended because its rounded terminals produce a friendlier, contemporary interface while retaining sufficient clarity for dense controls. The variable family supports a controlled range of weights and widths without loading many unrelated font files.

Use only the following UI weights unless a component specification explicitly requires otherwise:

- 400 — body text, values, menu items, normal labels.
- 600 — buttons, tabs, field labels, selected items, compact headings.
- 700 — page headings, major panel titles, launcher headlines.

Do not use synthetic bold or italic. Set `font-synthesis: none` in web-based surfaces.

### 6.6.2 CJK fallback

**Simplified Chinese fallback: Noto Sans SC Variable.**

Nunito Sans does not provide full Simplified Chinese coverage. Nova_A should use a deliberate fallback rather than allowing the operating system to choose unrelated fonts. Recommended editor stack:

```css
font-family: "Nunito Sans", "Noto Sans SC", system-ui, sans-serif;
```

The fallback must be bundled or resolved through a controlled application resource, not dependent on an arbitrary locally installed font. Chinese, English, German, numerals, punctuation, symbols, and mixed-language strings must be included in the visual regression suite.

### 6.6.3 Code and telemetry typeface

**Code and fixed-width telemetry: JetBrains Mono.**

Use JetBrains Mono for Script Studio, stack traces, hashes, vectors, timing columns, and other content that benefits from stable character width. Use a CJK monospaced fallback for Chinese comments where required. Recommended settings:

- Code size: 13 px at 100% UI scale.
- Line height: 1.40–1.45.
- Default weight: 400.
- Bold: 600 only for semantic emphasis.
- Ligatures: user-configurable; default off for maximum symbol literalness.

### 6.6.4 Typography scale

| Role | Size | Weight | Line height | Notes |
|---|---:|---:|---:|---|
| Metadata/caption | 11 px | 400 | 15 px | Paths, timestamps, secondary counters |
| Dense body | 12 px | 400 | 17 px | Tables and compact diagnostics |
| Standard body | 13 px | 400 | 19 px | Default editor text |
| Control label | 13 px | 600 | 18 px | Buttons, tabs, field labels |
| Section heading | 15 px | 700 | 20 px | Local panel title |
| Page heading | 20 px | 700 | 26 px | Full-page workspace heading |
| Launcher title | 40–48 px | 700 | 0.98–1.05 | Marketing surface only, responsive |

Rules:

- Do not use fractional font sizes.
- Do not scale text with CSS transforms or canvas bitmap scaling.
- Use tabular numerals for telemetry, time, memory, frame counts, and hashes.
- Use sentence case for buttons and tabs. Reserve all caps for very short category labels where proven beneficial.
- Truncated text must expose the full value by tooltip and keyboard focus.
- Use no more than three visible text weights in one view.

### 6.6.5 Anti-aliasing and high-DPI implementation

- Declare Windows Per-Monitor-V2 DPI awareness.
- Re-layout at the actual device scale factor when a window moves between monitors; do not bitmap-scale the whole editor.
- Render DOM/native text through the platform text stack. Do not convert editor text to canvas textures unless the component specifically requires it.
- For canvas overlays, rasterize at device-pixel ratio and regenerate after DPI change.
- Use native variable-font files for desktop and WOFF2 subsets for web distribution.
- Preload the primary font and avoid a visible fallback-font layout shift.
- Enable normal kerning and optical sizing where supported.
- Align 1-pixel borders and icon strokes to device pixels.
- Validate grayscale antialiasing and subpixel behavior on Windows, including Remote Desktop where supported.
- Disable any post-process sharpen or scale operation that produces halos around text.

### 6.6.6 Typography release gate

A release fails typography validation if any of the following occurs:

- A primary editor surface uses an undeclared UI font.
- Text clips at 100%, 125%, 150%, 175%, or 200% scale.
- Chinese fallback changes line height enough to overlap adjacent controls.
- A disabled control is unreadable at standard contrast.
- Toolbar icons or text are visibly blurred because the surface was bitmap-scaled.
- A font resource is missing from the web or Windows package.
- Font license notices are absent from the release's licensing documentation.

## 7.3 Defect severity

- **Severity 0 — Data loss / security compromise / unusable release:** project corruption, silent loss of user work, arbitrary-code boundary failure, installer damage, exported game cannot start on all Tier-1 environments.
- **Severity 1 — Release blocker:** crash in a common workflow, broken save/load, broken build, major feature unavailable, incorrect migration, severe accessibility blocker.
- **Severity 2 — Major:** workflow has a reliable workaround but significantly affects productivity or output correctness.
- **Severity 3 — Minor:** localized visual, wording, or low-impact behavior defect.
- **Severity 4 — Trivial:** cosmetic issue with no meaningful workflow impact.

A stable release contains zero unresolved Severity 0 and Severity 1 defects. Any accepted Severity 2 defect requires an owner, workaround, documented impact, and explicit release sign-off.

## 7.4 Reference environments

The team must pin exact hardware and software identifiers in `test-environments.json`. At minimum:

- **NOVA-WIN-LOW:** supported Windows release, 4-core x86-64 CPU, 8 GB RAM, integrated GPU, 1366×768, 100% scale.
- **NOVA-WIN-REF:** supported Windows release, 6-core/12-thread CPU, 16 GB RAM, mainstream GPU, 1920×1080, 100% and 125% scale.
- **NOVA-WIN-HIDPI:** supported Windows release, 16 GB RAM, 3840×2160, 150% and 200% scale, multi-monitor transition test.
- **NOVA-WIN-AMD, NOVA-WIN-INTEL, NOVA-WIN-NVIDIA:** representative GPU paths for renderer and driver validation.
- **NOVA-WEB-CHROMIUM, NOVA-WEB-FIREFOX:** current supported browser versions, clean profiles, local and HTTPS hosting.
- **NOVA-LINUX-REF and NOVA-MAC-REF:** required when those exporters reach Tier-1 or Tier-2 status.
- At least one machine must run with a non-English locale and a project path containing spaces, Chinese characters, accented Latin characters, and long path segments.

The exact operating-system and browser versions must be frozen for each release candidate. “Latest” is not a reproducible environment definition.

## 7.5 Release quality gates

For every 4.x minor release:

- 100% of mandatory P0 and P1 tests pass.
- At least 98% of the complete planned automated suite passes; all remaining failures are triaged and non-blocking.
- Zero Not Executed status for tests mapped to changed stable features.
- Core serialization, reference, build, and migration code meets at least 80% line and 70% branch coverage, with risk-based exceptions documented.
- No known data-loss path.
- 24-hour editor/runtime soak passes on NOVA-WIN-REF.
- Five consecutive clean builds from a clean workspace pass.
- Clean install, launch, project create, build, uninstall, and portable execution pass.
- Visual baselines pass at 100%, 125%, 150%, and 200% scaling.
- All release artifacts and hashes are generated by the release pipeline, not assembled manually.

For 5.0.0:

- All of the above, plus a 72-hour soak.
- Ten consecutive clean builds.
- Two independent machines reproduce the unsigned content payload hashes.
- Upgrade tests from 4.0.0 and 4.9.0 pass for every supported project schema.
- A release candidate remains open for at least 14 calendar days with no newly discovered Severity 0 or Severity 1 defect.
- Every stable public API has contract coverage and versioned documentation.

# 8. Common Release Engineering Standard

## 8.1 Versioning policy

Nova_A uses the following product-version rules:

- `1.x.x` change in the first field: major release with compatibility, architecture, or product-baseline significance.
- `x.1.x` change in the second field: minor release containing planned features and improvements.
- `x.x.1` change in the third field: patch release containing bug fixes, security fixes, compatibility corrections, and low-risk polish only.

Patch releases must not silently introduce new project schemas, new public APIs, new package permissions, or substantial workflow changes. A required compatibility break must move to a minor or major release.

Pre-release candidates may use labels such as `5.0.0-rc.1`, but the final release folder and filenames use the final numeric version only.

## 8.2 Mandatory release folder

Every release must be stored under:

```text
.\releases\vx.x.x\
```

For example:

```text
.\releases\v4.1.0\
.\releases\v5.0.0\
```

## 8.3 Mandatory root artifacts

Every release folder must contain exactly the following required artifacts, with the version substituted consistently:

```text
EDIT_LEDGER.md
LICENSE.md
Nova_A-vx.x.x-reference-projects.zip
Nova_A-vx.x.x-release-evidence.zip
Nova_A-vx.x.x-source.zip
Nova_A-vx.x.x-web.zip
Nova_A-vx.x.x-windows-x64.msi
Nova_A-vx.x.x-windows-x64-portable.exe
Nova_A-vx.x.x-windows-x64-setup.exe
RELEASE_NOTES.md
SHA256SUMS.txt
```

Additional files such as `THIRD_PARTY_NOTICES.md`, `SBOM.spdx.json`, or `BUILD_PROVENANCE.json` are recommended, but they do not replace any required artifact.

## 8.4 Artifact content requirements

### 8.4.1 EDIT_LEDGER.md

Must include:

- Version, release date, source commit, branch, build pipeline, and toolchain identity.
- Every user-visible addition, modification, removal, deprecation, migration, schema change, API change, dependency change, package-permission change, and build-target change.
- File or subsystem ownership for each material change.
- Linked issue, pull request, test IDs, and evidence path.
- Explicit statement for changes generated by automation.
- Confirmation that the ledger matches `RELEASE_NOTES.md` and the source tree.

### 8.4.2 LICENSE.md

Must include:

- Nova_A's applicable license text and copyright notice.
- License policy for bundled templates and reference assets.
- Required notices for Nunito Sans, Noto Sans SC, JetBrains Mono, and all other redistributed third-party components.
- A clear route to full third-party notices if they are placed in an additional file.
- No release may bundle a font, library, asset, or tool without a verified redistribution right.

### 8.4.3 Nova_A-vx.x.x-reference-projects.zip

Must include version-pinned projects that exercise all stable subsystems. At minimum:

- Empty 2D.
- Platformer.
- Top-down.
- Physics Sandbox.
- UI Showcase.
- Asset-pipeline and migration fixture project.
- Animation and state-machine project.
- Rendering/particles project.
- Audio/mixer project.
- Build/export smoke project.

Every reference project must contain a README, expected behavior, test IDs, required packages, target platforms, and known limitations. Reference projects must build in CI.

### 8.4.4 Nova_A-vx.x.x-release-evidence.zip

Must contain the evidence structure in Section 7.8 and prove:

- Test execution and outcomes.
- Coverage.
- Visual-regression status.
- Migration and fault-injection results.
- Performance and soak results.
- Security and package tests.
- Installer and portable validation.
- Web browser validation.
- Reproducibility comparison.
- Environment identity.
- Final release sign-off.

### 8.4.5 Nova_A-vx.x.x-source.zip

Must contain:

- Complete source needed to build the release.
- Pinned dependency and toolchain manifests.
- Build scripts and CI definitions.
- Test sources and fixtures, except secrets or legally restricted material.
- No build cache, local credentials, personal paths, private keys, or unrelated generated artifacts.
- A top-level build README with clean-environment instructions.
- Source archive hash recorded in `SHA256SUMS.txt` and release evidence.

### 8.4.6 Nova_A-vx.x.x-web.zip

Must contain:

- The supported web editor or web distribution promised by the release.
- No desktop-only binaries, private source maps, development endpoints, editor secrets, or local absolute paths.
- Required font resources and licenses.
- A deployment README specifying HTTPS, MIME types, caching, cross-origin isolation or other headers when required, and supported browsers.
- A manifest with build version, commit, content hashes, and runtime capabilities.

### 8.4.7 Windows MSI, setup EXE, and portable EXE

All three Windows artifacts must:

- Report the exact release version.
- Be built from the same approved source commit and content manifest.
- Pass malware scanning and internal security review.
- Avoid unsigned-success messaging; signing status must be truthful.
- Support clean launch on Tier-1 Windows environments.
- Preserve user projects and settings during upgrade and uninstall.
- Write only documented locations.
- Include or link license information before installation where applicable.

Specific behavior:

- MSI: enterprise-compatible install, repair, upgrade, and uninstall behavior.
- Setup EXE: guided user installation with clear scope and path choices.
- Portable EXE: no installer dependency; user data location and portability rules documented.

### 8.4.8 RELEASE_NOTES.md

Must include:

- Release summary and intended audience.
- Additions, improvements, removals, deprecations, compatibility changes, migrations, security changes, and known issues.
- Supported platform tiers.
- Project schema and Rhai/plugin API versions.
- Upgrade and rollback instructions.
- Clear notice for experimental features.
- Links or paths to reference projects, test evidence, and documentation.

### 8.4.9 SHA256SUMS.txt

Must include SHA-256 for every required root artifact and any additional root artifact. The file must be generated after final artifact creation and verified by an independent release step. Filenames must match exactly.

## 8.5 Release pipeline rules

- Build from a clean, pinned environment.
- Tag the exact source commit before final artifact generation.
- Do not rebuild an individual artifact after sign-off without invalidating and regenerating all evidence and checksums.
- Separate unsigned reproducibility comparison from final signing, because signatures may contain timestamps or certificate metadata.
- Generate installers, portable build, web archive, source archive, reference projects, evidence, notes, ledger, and checksums from one release pipeline.
- Store signing credentials outside the source tree and release archives.
- Preserve release logs and provenance according to the support policy.
- A human release lead and an independent verifier must sign `release-signoff.md`.

## 8.6 Patch-release policy

A patch release may include:

- Crash fixes.
- Data-integrity fixes.
- Security fixes.
- Installer or platform compatibility fixes.
- Performance regressions with no user-facing workflow redesign.
- Localization, accessibility, documentation, and visual corrections.
- Dependency updates that preserve compatibility and pass the full affected test matrix.

A patch release may not include:

- New project format or schema unless required to prevent data loss and explicitly approved as an emergency exception.
- New stable public API surface.
- New package permissions.
- Major UI navigation changes.
- New export target.
- Silent removal of supported behavior.

# 9.2 Nova_A 4.2.0 — Project Integrity, Deterministic Serialization, Undo/Redo, Recovery, and Migration

## Release objective

Make project editing safe under normal work, crashes, interrupted writes, schema upgrades, external changes, and destructive operations. This release is the data-integrity foundation for 5.0.

## Remove or deprecate

- Remove silent in-place migration without preview, backup, report, and rollback.
- Remove direct multi-file writes that can leave a partially updated project.

- Remove save operations that bypass the central transaction and undo services.
- Deprecate unstable field ordering, path-based object identity, and reference formats that change merely because files move.

## Add functionality

### Project transaction service

- Introduce atomic project transactions for scene, asset, script metadata, build settings, package lockfile, UI, and animation changes.
- Use temporary files plus atomic replacement or an equivalent platform-safe strategy.
- Add write-ahead journal, transaction ID, affected-file manifest, checksum, and recovery state.
- Add disk-space preflight, permission preflight, cancellation boundaries, and error classification.

### Deterministic serialization

- Define canonical ordering, whitespace, line endings, floating-point formatting, identifier formatting, and reference encoding.
- Separate authored source data from generated import/cache data.
- Add schema validator and deterministic re-save command.
- Add semantic diff metadata for scenes, prefabs, and resources.

### Undo and redo

- Create a central command model covering scene edits, inspector changes, hierarchy changes, asset operations, animation keys, UI layout, project settings, packages, and build presets.
- Add named history, grouped operations, nested transactions, memory budget, redo invalidation, and history clearing rules.
- Add an Undo History panel with affected resource and timestamp.

### Autosave and crash recovery

- Add recovery checkpoints separate from manual saves.
- Add abnormal-exit detection and a Recovery Browser with preview, diff, restore, discard, and open-copy actions.
- Never overwrite the last known-good manual save with an unverified recovery checkpoint.

### Migration and repair

- Add migration dry run, compatibility report, estimated changes, project backup, step-by-step log, rollback, and deterministic re-run.
- Support all project schemas promised by 4.0.0, including visible schemas 5 through 29, unless an explicit support exception is approved.
- Add read-only repair mode, missing-reference mapping, stale-cache rebuild, and manifest reconstruction where safe.
- Add project-open locking and a clear read-only option when another process owns the project.

### External-change handling

- Add file watcher with self-change suppression, conflict detection, reload, compare, keep editor, and keep disk options.
- Add safe handling for source-control branch changes and large external updates.

## Modify and improve

- Make Project Health the front end for integrity, schema, recovery, migration, and reference problems.
- Change launcher Import Project into a guided Open, Add existing, Migrate older project, or Import archive workflow.
- Show unsaved state consistently in scene, script, animation, UI, settings, and build-preset tabs.
- Make all destructive dialogs state the exact resource count and provide reversible action where possible.
- Record transaction and migration summaries in Task Center and diagnostic bundles.

## Testing process

- Run serialization round-trip and deterministic-byte tests on all reference projects.
- Run migration fixtures for every supported schema, including malformed, missing, duplicated, and future-version fields.
- Inject process termination at every project-write stage and verify recovery.
- Inject disk-full, read-only, permission-denied, file-in-use, antivirus-delay, long-path, Unicode-path, and network-path conditions.
- Execute at least 10,000 mixed undo/redo commands across scenes, assets, animation, UI, and settings.

## Testing and acceptance requirements

- No injected interruption may corrupt the last valid manual save.
- A successful deterministic re-save of an unchanged project produces no semantic change and stable canonical output.
- Every project-changing stable control is routed through undo/redo or has an explicit documented exception.
- Every supported old schema migrates or fails before mutation with an actionable reason.
- Recovery Browser restores the newest valid checkpoint and never silently chooses between conflicting states.
- Move/rename and migration operations leave zero unresolved references in the reference-project suite.
- No Severity 0 or Severity 1 issue remains in data-integrity tests.

## Release requirements

- Provide the complete mandatory artifact set under `.\releases\v4.2.0\`.
- Include serialization specification, schema compatibility matrix, migration fixtures/results, fault-injection logs, undo coverage report, recovery demonstrations, parser-fuzz summary, and deterministic-output comparisons in release evidence.

# 10. Program Governance and 5.0 Definition of Done

## 10.1 Feature lifecycle

Every capability must have one lifecycle state:

- **Internal:** visible only in development builds; no compatibility promise.
- **Experimental:** opt-in, documented limitations, may change, excluded from production-readiness claims.
- **Beta:** end-to-end workflow exists and is tested, but compatibility or performance may still change.
- **Stable:** documented, migrated, automated, supported on declared platform tiers, and covered by release gates.
- **Deprecated:** still supported for a documented period, with replacement and migration guidance.
- **Removed:** no longer available in new projects; read-only import or migration may remain if promised.

A tab, button, API, package, template claim, or release note may not use Stable unless authoring, runtime, serialization, migration, documentation, and tests all meet the stable definition.

## 10.2 Change-control gates

Before implementation begins:

- Product owner approves user problem and scope.
- Architecture owner approves data model and subsystem boundary.
- UX owner approves information architecture and component use.
- QA owner approves test strategy and acceptance criteria.
- Release owner approves compatibility and artifact impact.

Before merge:

- Automated tests pass.
- New controls have accessible names, keyboard behavior, design tokens, telemetry where necessary, and test IDs.
- New project data has schema, migration, deterministic serialization, undo/redo, recovery, and diff behavior.
- New APIs have documentation, contract tests, and lifecycle state.
- New package permissions or network behavior receive security review.

Before release:

- Project Health rules are updated.
- Reference projects demonstrate the stable workflow.
- Manual and API documentation match the build.
- Evidence and release artifacts are generated from the final commit.
- No known Severity 0 or Severity 1 defect remains.

## 10.3 Required engineering metrics

Track at least:

- Crash-free editor sessions.
- Data-loss and recovery incidents.
- Startup time to launcher and project-ready state.
- Project open/save times by reference-project size.
- Import throughput and cache hit rate.
- Workspace switch, search, hierarchy, Inspector, and Script Studio latency.
- Play-start and stop time.
- Frame, physics, script, rendering, animation, audio, asset, and editor-overhead budgets.
- Memory after repeated play/stop, import/reimport, and scene switches.
- Build duration, cache effectiveness, and reproducibility status.
- Automated test count, pass rate, flaky-test rate, coverage, and unexecuted tests.
- Accessibility and visual-regression failures.
- Package security and dependency findings.
- Documentation coverage for stable features and APIs.

Metrics must use pinned environments and historical baselines. A faster high-end machine is not a valid way to hide a regression.

# Appendix B. Terminology

- **Atomic save:** a save operation that leaves either the complete old state or the complete new state, not a partial mixture.
- **Canonical serialization:** one stable textual or binary representation for equivalent project data.
- **Content inclusion rule:** an explicit policy defining which assets and dependencies enter an exported game.
- **Contract test:** an automated test proving a public API, file format, CLI, plugin contract, or manifest behaves as documented.
- **Deterministic artifact:** an output that is equivalent when produced from the same declared inputs and toolchain, subject to documented signing/timestamp exceptions.
- **Editor-only content:** resources used by the editor but excluded from exported games.
- **Golden image:** an approved reference rendering compared against later output within defined tolerances.
- **Hot reload:** replacing code or resources during a running session without a full restart, under documented compatibility rules.
- **Per-Monitor-V2 DPI awareness:** Windows behavior in which an application re-renders and re-lays out for the scale of the monitor containing the window.
- **Prefab:** a reusable authored object hierarchy or scene fragment with instances and controlled overrides.
- **Project schema:** the versioned structure of project data within a project format.
- **Release evidence:** machine- and human-readable proof that required tests, builds, migrations, security checks, and clean-machine validations were performed.
- **Tier-1 platform:** a platform that receives complete build, runtime, regression, installer/deployment, and support validation for the release.
- **Visual regression:** automated comparison of editor or runtime screenshots against approved baselines.

# Appendix C. Final Planning Position

Nova_A 4.0.0 already displays many of the surfaces expected from a serious 2D engine. The next major risk is not lack of visible breadth. It is the possibility that breadth exceeds integration, reliability, test evidence, and user comprehension.

The roadmap therefore treats 4.1.0–4.2.0 as non-negotiable foundations, 4.3.0–4.8.0 as subsystem completion, 4.9.0 as release-system and ecosystem closure, and 5.0.0 as an evidence-based stability declaration. Features that cannot satisfy the relevant acceptance gate should remain Beta or Experimental rather than being marketed as stable.
