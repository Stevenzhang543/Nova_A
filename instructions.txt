# Nova_A 3.0.0 Product Capability Audit and Development Roadmap

## Version 3.1.0 through Version 4.0.0

**Document ID:** NOVA-A-PLAN-3.1-4.0
**Status:** Development Planning Baseline
**Prepared for:** Code Department
**Prepared by:** Chief Development Planner
**Date:** 16 August 2026
**Product reviewed:** Nova_A 3.0.0, project format 2, schema 22


## Document Purpose

This document has four purposes:

1. Identify the functionality that is visibly present in Nova_A 3.0.0.
2. Identify the technical, workflow, usability, stability, and product gaps between the current engine and a mature developer-facing 2D engine.
3. Identify low-value, duplicated, misplaced, or confusing features that should be removed, merged, relocated, or redesigned.
4. Convert the findings into an implementable release plan from version 3.1.0 through version 4.0.0.

The plan deliberately prioritizes complete development workflows, project safety, and engineering quality over adding more visible panels. A mature engine is not defined by the number of buttons it displays. It is defined by whether a developer can create, debug, version, export, maintain, and upgrade a real game without losing work or fighting the tool.


# 1. Executive Assessment

## 1.1 Overall conclusion

Nova_A 3.0.0 presents a broad and visually coherent editor surface. The screenshots show project templates, a scene editor, an object hierarchy, an inspector, an asset browser, a package manager, a Rhai script editor, an embedded game view, a console, physics settings, animation tooling, rendering and shader tooling, tilemap tooling, UI tooling, profiling, build configuration, localization-related controls, input mapping, save-data inspection, plugin security controls, and optional networking concepts.

That breadth is a strong foundation. It also creates the largest product risk: the editor currently appears to expose more systems than can be verified as complete, integrated, and production-safe. The main requirement for the 3.x roadmap is therefore not “add every missing feature immediately.” It is “turn the current breadth into reliable end-to-end workflows.”

Based on the screenshots alone, Nova_A should be treated as an **advanced prototype or early alpha editor platform**, not yet as a production-grade engine. This classification does not mean the underlying implementation is poor. It means the screenshots do not demonstrate the durability requirements expected from a mature engine: deterministic project serialization, safe migrations, complete undo and redo, dependency-preserving asset operations, debugging depth, platform export validation, crash recovery, long-duration stability, API compatibility policy, extensive documentation, and automated release evidence.

## 1.2 Strongest current areas

The strongest visible areas are:

- A consistent dark visual system and recognizable editor structure.
- Template-based project creation for blank 2D, platformer, top-down, physics, UI, and networking use cases.
- A multi-workspace editor that separates design, scripting, animation, UI, and debugging.
- An integrated asset browser with many declared asset types.
- A package manager with offline mode, compatibility states, a lock concept, and plugin security controls.
- A built-in Rhai editor with lifecycle functions, exported values, input access, physics calls, diagnostics, and tests.
- Physics-oriented settings, a 32-layer collision matrix, rigid-body controls, and debug visualization concepts.
- A profiler-like “Production Lab” with frame timing, memory, render, script, physics, animation, and audio categories.
- Rendering diagnostics and custom GLSL ES shader editing.
- Dedicated tilemap, animation, UI, input, build, and settings surfaces.
- A release-oriented build panel rather than a single opaque “Export” button.

## 1.3 Highest-risk gaps

The highest-risk gaps are:

- The project, scene, resource, and reference model is not visibly defined well enough for large projects or source control.
- Undo, redo, crash recovery, autosave restoration, file migration, and corruption recovery are not visibly complete.
- Asset import, reimport, metadata, thumbnails, dependency tracking, rename-safe references, and hot reload are not demonstrated.
- The scene and object workflow is too shallow in the screenshots: basic object creation is visible, but robust multi-object editing, prefab overrides, scene instancing, property reset, property validation, and complex gizmos are not.
- The scripting editor shows a useful shell, but not a production debugger with breakpoints, stack frames, locals, watches, conditional breakpoints, hot reload rules, or a stable API contract.
- Rendering appears tied to WebGL2 in project information. A mature desktop editor needs a defined native runtime path, renderer capability tiers, robust shader validation, sprite batching, texture and font pipelines, render targets, and cross-GPU regression testing.
- The animation, tilemap, UI, navigation, AI, streaming, networking, audio, and package systems are visibly broad but not proven deep.
- Build support appears centered on Windows x86-64. Build reproducibility, command-line export, signing, symbols, CI, Linux, macOS, web validation, and clean-machine tests are not demonstrated.
- There is no visible API lifecycle, compatibility policy, long-term support policy, or systematic migration process.
- Many advanced or diagnostic functions are placed in general settings or permanent navigation, creating clutter and confusing information architecture.

## 1.4 Product direction for version 4.0.0

Nova_A 4.0.0 should not attempt to match every feature in every competing engine. It should establish a clear production baseline:

- A stable, documented 2D runtime.
- A deterministic, migration-safe, version-control-friendly project format.
- A complete scene, resource, prefab, and asset pipeline.
- A productive 2D editor with strong inspector, hierarchy, gizmo, camera, sprite, tilemap, animation, UI, physics, input, audio, and debugging workflows.
- One Tier-1 native desktop target and one Tier-1 web target, with additional targets clearly labeled by support level.
- A stable Rhai API and a real debugger.
- A package and plugin system with dependency resolution, permissions, signatures, lockfiles, and rollback.
- Automated quality gates and evidence for every release.
- No unresolved severity-0 or severity-1 defects at release.

## 1.5 Immediate planning decisions

The following decisions should be approved before 3.1.0 development begins:

1. **Feature freeze for unsupported surfaces.** Networking, AI, world streaming, object pooling, and advanced material tooling must be labeled Experimental until they pass end-to-end tests.
2. **Core-before-breadth policy.** Project safety, scene and resource integrity, undo and redo, migration, import, debugging, and export reliability receive priority over new visible subsystems.
3. **Information architecture reset.** Duplicate workspaces and misplaced diagnostics must be merged or relocated.
4. **Tiered platform policy.** The team must name Tier-1, Tier-2, and Experimental platforms rather than implying equal support.
5. **Release evidence as a mandatory artifact.** A release is not complete when binaries are built; it is complete when tests, provenance, checksums, migration evidence, and clean-machine validation are captured.


# 2. Review Method and Evidence Limits

## 2.1 Evidence basis

This assessment is based on nineteen screenshots of Nova_A 3.0.0. The screenshots cover the project manager, design workspace, resource browser, package manager, embedded run view, console, animation panel, profiler, rendering panel, tilemap panel, world tools, project information, build settings, script editor, general settings, input mappings, engine diagnostics, collision matrix, plugin and save-data settings, and UI workspace.

No source code, executable, project files, crash logs, profiler captures, export outputs, API reference, schema specification, package manifest, or automated test report was supplied. Therefore:

- A visible button is treated as **UI-exposed functionality**, not proof that the workflow is complete.
- A status label is treated as **declared capability**, not proof of runtime correctness.
- Stability, performance, determinism, backward compatibility, and security cannot be confirmed from screenshots.
- Features not visible in the screenshots are classified as “not evidenced,” not automatically “absent.”

## 2.2 Capability confidence labels

This document uses three confidence labels:

- **Observed:** the screenshot directly shows the function or control.
- **Implied:** the interface strongly suggests the function, but the complete workflow is not visible.
- **Not evidenced:** the screenshots do not establish that the capability exists.

## 2.3 Competitive benchmark

The benchmark is category-based rather than a one-to-one imitation of another product. Current mature 2D engines publicly document broad support for scene and asset editing, scripting and debugging, profiling, physics, input, audio, animation, tilemaps, GUI systems, localization, package or extension systems, platform export, and automation. The benchmark for Nova_A is therefore the completeness and reliability of these workflows, not visual similarity to a specific editor.

# 5. Maturity Gap Analysis

## 5.1 Product architecture and subsystem boundaries

### Current issue

The current interface exposes core engine systems, editor utilities, debug tools, optional packages, and experimental features at nearly the same visual level. “World Tools,” networking, profiler functions, save-data inspection, plugin configuration, and static project information all compete for permanent navigation space.

### Why it matters

When the distinction between core runtime, editor-only tooling, optional packages, and experimental modules is unclear, users cannot judge what is stable. Internally, this usually creates coupling: systems depend on editor state, packages assume privileged access, and project formats accumulate special cases.

### Required direction

Nova_A needs four explicit product layers:

1. **Core runtime:** scene graph, resources, rendering, physics, audio, input, scripting, UI, and lifecycle.
2. **Editor:** authoring, import, inspection, debugging, profiling, and build orchestration.
3. **Official packages:** networking, behavior tools, advanced post-processing, platform integrations, and optional templates.
4. **Third-party extensions:** permissioned and versioned plugins using a documented extension API.

Every feature must declare its layer, stability level, serialization impact, API surface, and test owner.

## 5.2 Project format, serialization, migration, and compatibility

### Current issue

The screenshots display project format 2 and schema 22, but not the format specification, migration path, backup strategy, deterministic save rules, or compatibility policy.

### Missing capabilities

- Human-readable or diffable scene and resource representation.
- Stable object and asset identifiers.
- Deterministic ordering and numeric formatting.
- Schema migration registry.
- Dry-run migration report.
- Automatic backup before migration.

# 6. User-Experience Audit

## 6.1 What should be retained

The following concepts are valuable and should be retained:

- The overall dark visual language and blue accent.
- Template-based project creation.
- A central 2D viewport with hierarchy and inspector.
- Dedicated script, animation, UI, and debug workspaces.
- An integrated resource browser.
- Embedded game preview.
- Package security and offline concepts.
- A profiler and render diagnostics.
- Separate project and build configuration.
- Input-action mapping.
- Collision-layer management.
- Responsive UI, localization, and accessibility as explicit product areas.

The problem is not that these concepts exist. The problem is that their current grouping, naming, and depth are inconsistent.

## 6.2 Features or panels that are low-value in their current form

1. **“Production Lab”**
   - **User problem:** The name is promotional and does not communicate profiling or diagnostics. It overlaps Debug.
   - **Recommended action:** Rename it to **Profiler** and integrate it into the Debug workspace.
   - **Target:** 3.1.0.

2. **“Presentation” bottom dock plus “UI” top workspace**
   - **User problem:** Two labels appear to cover UI, themes, localization, audio, and accessibility. Users cannot predict which one to open.
   - **Recommended action:** Merge them into one **UI** workspace with contextual subpanels.
   - **Target:** 3.1.0 and 3.6.0.

3. **“World Tools” monolithic dock**
   - **User problem:** Character, navigation, AI, streaming, and pooling are unrelated workflows and are permanently visible.
   - **Recommended action:** Split them into components and optional packages. Keep Navigation core; move AI, streaming helpers, and object-pool tools behind packages or project capabilities.
   - **Target:** 3.1.0 and 3.8.0.

4. **Project information cards as a full dock**
   - **User problem:** Engine version, schema, scene count, asset count, and backend do not justify a permanent large panel.
   - **Recommended action:** Move them to the Project Settings header and a compact Project Health page.
   - **Target:** 3.1.0.

5. **Save-data inspector inside general Settings**
   - **User problem:** Runtime save inspection is a debugging workflow, not an editor preference.
   - **Recommended action:** Move it to Debug > Data Inspector.
   - **Target:** 3.1.0.

6. **Live engine diagnostics inside Settings**
   - **User problem:** Runtime counters are not configuration.
   - **Recommended action:** Move them to Profiler > Runtime Diagnostics.
   - **Target:** 3.1.0.

7. **Plugin controls duplicated between Package Manager and Settings**
   - **User problem:** The user must search two places for package and plugin state.
   - **Recommended action:** Centralize installation, enablement, permissions, lockfile, and security in Package Manager.
   - **Target:** 3.1.0 and 3.9.0.

8. **Unlabelled 32-by-32 collision matrix**
   - **User problem:** A large numeric grid is difficult to understand and easy to misconfigure.
   - **Recommended action:** Add named layers, row and column labels, presets, search, symmetric editing, and a compact pair editor. Keep the full matrix as an advanced view.
   - **Target:** 3.4.0.

9. **Single-letter top controls such as H, I, and B**
   - **User problem:** Their meaning is not discoverable and may be language-dependent.
   - **Recommended action:** Replace them with standard icons, text tooltips, and configurable shortcuts.
   - **Target:** 3.1.0.

10. **Long horizontal row of resource-type chips**
    - **User problem:** The row consumes space, wraps poorly, and becomes harder to scan as types grow.
    - **Recommended action:** Replace it with a searchable filter menu, favorites, and saved filters.
    - **Target:** 3.2.0.

11. **Raw JSON for shader uniforms and textures**
    - **User problem:** It is error-prone for ordinary users and duplicates information the shader compiler can infer.
    - **Recommended action:** Keep JSON as an advanced mode; generate a typed uniform inspector by default.
    - **Target:** 3.7.0.

12. **Networking template presented equally with core templates**
    - **User problem:** It may imply production readiness even if the package is experimental.
    - **Recommended action:** Add an Experimental badge, compatibility notice, and explicit package version. Hide it unless experimental templates are enabled.
    - **Target:** 3.1.0.

13. **AI and object-pool tabs permanently exposed**
    - **User problem:** These are not universal engine-authoring tasks.
    - **Recommended action:** Move them to optional official packages and component search.
    - **Target:** 3.8.0.

14. **Empty inspector offering only UI object creation**
    - **User problem:** It incorrectly suggests UI is the primary object category and omits common game objects.
    - **Recommended action:** Replace it with a universal Create Object or Add Component palette.
    - **Target:** 3.3.0.

## 6.3 Layout and visual hierarchy problems

### Excessive permanent navigation

The interface has top workspaces, a left rail, a bottom dock row, scene tabs, and object inspector categories. Each is individually reasonable, but together they create too many simultaneous navigation systems. A user should not have to distinguish “Debug workspace,” “Game section,” “Console dock,” “Production Lab,” “Engine Diagnostics,” and “Rendering Diagnostics” before they can inspect a problem.

### Flat priority hierarchy

Many controls use similar border weight, background value, and blue selection states. Major actions, current workspace, selected object, active tool, focused field, and toggled option can appear visually similar. The editor needs a stricter semantic color and elevation system:

- Accent blue for primary selection and primary action.
- Neutral focus ring for keyboard focus.
- Green only for confirmed success.
- Amber for warnings and experimental features.
- Red for destructive or failed state.
- Distinct disabled styling with sufficient contrast.

### Dense settings cards

The settings pages contain many large cards with long vertical scrolling but no visible search, category tree, “modified only” filter, or reset-to-default workflow. Settings should be searchable and support project-level versus editor-level scope.

### Imbalanced space usage

Several screenshots show a large empty game viewport while high-density controls are compressed into the bottom or right edge. Docks should be resizable, collapsible, and detachable. Empty states should use the space to teach the next action rather than leaving a blank area.

### Small labels and control targets

At the shown resolution, many controls and labels are visually small. UI scale exists, which is good, but the default must be validated at 1366-by-768, 1920-by-1080, high-DPI 4K, and 125/150/200 percent operating-system scaling. Click targets and focus indicators must remain usable.

### Mixed terminology

The interface mixes standard engine terms with product-specific terms. Product-specific names can be retained only when they improve understanding. “Profiler,” “Scene,” “Inspector,” “Asset Browser,” “Animation,” “Tilemap,” “Build,” and “Package Manager” should remain conventional. Promotional names should not replace operational names.

## 6.4 First-launch window behavior

Management requires the first roadmap release to open the application at full size. The implementation should be:

- On first launch, the editor opens in **borderless fullscreen on the active monitor**.
- A setting named **Launch editor in fullscreen** is enabled by default.
- F11 toggles between borderless fullscreen and the last valid windowed state.
- After the first successful session, the editor restores the last valid monitor, window state, size, and position.
- If the stored monitor no longer exists, the window is moved to the primary monitor and reopened in borderless fullscreen.
- The default fullscreen implementation must be borderless rather than exclusive so task switching, dialogs, multiple monitors, and accessibility tools continue to work.

This implements the required full-screen default while avoiding the usability problems of an exclusive game-style display mode.

## 6.5 Critical user workflows that must become first-class

### Beginner workflow

Create a platformer from a template, replace art, edit a level, change input, run, diagnose an error, and export a Windows or web build. Every step must have a visible next action and official documentation.

### Programmer workflow

Create a component, write Rhai code, inspect API documentation, set a breakpoint, run, inspect locals, hot reload safely, write a test, and use the same test in CI.

### Designer workflow

Create reusable prefabs, instantiate them, override values, edit tilemaps, connect triggers, set collision layers, animate objects, and validate missing references.

### UI workflow

Build a responsive menu, preview multiple resolutions, navigate by keyboard and controller, localize strings, test pseudolocalization, and verify accessibility labels and focus order.

### Release-engineer workflow

Validate the project, run tests, build from the CLI, produce signed artifacts, verify checksums, install on a clean machine, run reference projects, and archive release evidence.


# 7. Product and Engineering Principles for the 3.x Roadmap

1. **Complete workflows before additional panels.** A feature is not complete until it can be created, edited, saved, reopened, duplicated, migrated, undone, debugged, documented, and tested.
2. **Core and optional features must be separated.** Experimental networking, AI, streaming helpers, and specialized utilities should not appear as stable core features.
3. **All persistent data must be versioned.** Scenes, resources, settings, packages, saves, and build presets require schema versions and migrations.
4. **Editor operations must be transactional.** A multi-file operation must either complete or roll back.
5. **Every reference must survive normal project organization.** Renaming or moving assets must not silently break scenes.
6. **Every public API requires documentation and compatibility tests.** API design is a product contract.
7. **Every release requires evidence.** The release folder is incomplete without test and provenance artifacts.
8. **Performance must be measured against reference projects.** “Feels fast” is not an acceptance criterion.
9. **Accessibility and localization are workflows, not toggles.** They require test assets, navigation tests, and layout validation.
10. **The editor must be recoverable.** Safe mode, layout reset, package disable, autosave restore, and migration rollback are mandatory.


# 8. Common Test and Release Standard

## 8.1 Defect severity

- **S0 — Release blocker:** data loss, security compromise, project corruption, installer failure, unusable editor startup, or widespread export failure.
- **S1 — Critical:** crash in a common workflow, broken migration, major reference loss, debugger unusable, or a Tier-1 platform unable to run a reference project.
- **S2 — Major:** incorrect behavior with a workaround, serious UX regression, substantial performance regression, or incomplete documentation for a core feature.
- **S3 — Minor:** cosmetic defect, uncommon edge case, wording issue, or small inconsistency.

No stable minor or major release may ship with open S0 or S1 defects.

## 8.2 Required test layers

Every planned release must use the applicable layers below:

1. Unit tests for runtime and editor logic.
2. Serialization round-trip tests.
3. Migration tests using archived projects.
4. Integration tests across scene, resource, script, physics, render, audio, input, and build boundaries.
5. Editor end-to-end automation for common user tasks.
6. Golden-image rendering tests with explicit tolerance.
7. Performance benchmarks and regression budgets.
8. Long-duration soak tests.
9. Fuzz tests for parsers, project files, scripts, shaders, package manifests, and imported assets.
10. Accessibility, keyboard navigation, high-contrast, reduced-motion, and scaling tests.
11. Localization and pseudolocalization tests.
12. Clean-machine installer, portable, web, and export tests.
13. Package permission and supply-chain tests.
14. Manual exploratory tests on reference projects.

## 8.3 Reference environment

At minimum, testing must include:

- Windows 11 x86-64 on a mainstream six-core CPU, 16 GB RAM, SSD, and integrated graphics.
- Windows 11 x86-64 on a discrete GPU from each supported vendor family.
- High-DPI and standard-DPI displays.
- 1366-by-768, 1920-by-1080, 2560-by-1440, and 3840-by-2160 editor layouts.
- Current supported Chromium, Firefox, and WebKit-based browsers for web exports.
- Offline package and documentation operation.
- Clean user profile and upgraded user profile.

Linux and macOS must be added to the matrix when they become supported tiers.

## 8.4 Common release folder and mandatory artifacts

Every release must be stored in:

```text
.\releases\vx.x.x
```

The folder must contain exactly named mandatory top-level artifacts:

```text
EDIT_LEDGER.md
LICENSE.md
Nova_A-vx.x.x-reference-projects.zip
Nova_A-vx.x.x-release-evidence.zip
Nova_A-vx.x.x-source.zip
Nova_A-vx.x.x-web.zip
Nova_A-vx.x.x-windows-x64.msi
Nova_A-vx.x.x-windows-x64-portable.exe
Nova_A-vx.x.x-windows-x64-setup.exe
RELEASE_NOTES.md
SHA256SUMS.txt
```

Additional evidence such as a software bill of materials, third-party notices, benchmark CSV files, signatures, symbol archives, screenshots, and CI logs should be placed inside `Nova_A-vx.x.x-release-evidence.zip` unless management later approves more top-level artifacts.

## 8.5 Artifact content requirements

### EDIT_LEDGER.md

Must include:

- Release version and source tag.
- Changed files or generated change summary.
- Schema changes.
- Public API additions, changes, deprecations, and removals.
- Migration steps.
- Known compatibility impact.
- Third-party dependency changes.

### Nova_A-vx.x.x-reference-projects.zip

Must include version-pinned reference projects relevant to the release. Each project must contain a README, expected output, test controls, and a validation command.

### Nova_A-vx.x.x-release-evidence.zip

Must include:

- CI summary.
- Unit and integration test results.
- Editor end-to-end results.
- Migration results.
- Performance comparison.
- Installer and clean-machine test report.
- Security and package-permission test report when applicable.
- Accessibility and localization report when applicable.
- Known-issue disposition.
- Source tag and build environment metadata.
- Software bill of materials and third-party license inventory.

### Nova_A-vx.x.x-source.zip

Must be generated from the signed release tag, exclude unrelated local files, and contain build instructions.

### Nova_A-vx.x.x-web.zip

Must be a deployable web package with version metadata, integrity checks, and a README describing hosting requirements.

### Windows artifacts

The MSI, portable executable, and setup executable must be built from the same source tag. Stable releases must be code-signed when signing infrastructure is available. The installer and uninstaller must be tested on a clean machine.

### RELEASE_NOTES.md

Must include highlights, user-visible changes, breaking changes, migration notes, known issues, supported platforms, package API compatibility, and upgrade and rollback instructions.

### SHA256SUMS.txt

Must contain checksums for every mandatory artifact except itself. Checksums must be generated after final signing and packaging.

## 8.6 Patch-release policy

A patch release such as 3.1.1 may contain defect fixes, security fixes, performance corrections, documentation corrections, and compatibility restorations. It must not introduce a new project schema, new public API family, new asset type, or major workflow. Emergency migration repair is allowed only when it restores compatibility and is fully tested.


# 9. Detailed Development Roadmap

The roadmap is dependency-driven rather than feature-count-driven. Each release closes a complete production workflow and establishes contracts required by the next release. A version must not move forward merely because its interface exists; it must meet the test, evidence, migration, documentation, and release gates defined in Sections 8 and 11.

Planned sequence:

1. **3.1.0 — Editor foundation:** fullscreen-first launch, workspace simplification, undo, autosave, recovery, discoverability, and consistent feedback.
2. **3.2.0 — Data foundation:** project schema, deterministic serialization, scenes, prefabs, stable IDs, asset imports, dependencies, and migration.
3. **3.3.0 — Core authoring:** complete 2D object creation, viewport tools, inspector, camera, sprites, and hierarchy productivity.
4. **3.4.0 — Physics:** complete body and shape model, queries, events, character controller, layers, joints, and deterministic validation.
5. **3.5.0 — Scripting:** Rhai API v1, code intelligence, debugger, safe hot reload, tests, and API compatibility policy.
6. **3.6.0 — Interaction:** animation, responsive UI, input, localization, and accessibility as integrated production workflows.
7. **3.7.0 — Presentation:** renderer architecture, 2D rendering, materials, shaders, particles, fonts, color management, and audio.
8. **3.8.0 — Worlds and data:** Tilemap 2.0, navigation, large-world streaming, save migration, and optional world packages.
9. **3.9.0 — Productization:** reproducible builds, platform tiers, package trust, source-control workflows, documentation, and the 4.0 release candidate.
10. **4.0.0 — Stable baseline:** compatibility freeze, migration safety, final quality gates, reference content, and production support policy.

# 9.1 Nova_A 3.1.0 — Editor Usability, Safety, and Workspace Baseline

# 11. Definition of Done for Any User-Facing Feature

A feature is complete only when all applicable conditions are true:

- It can be created through the editor or documented API.
- It can be configured and validated.
- It can be saved, closed, reopened, and migrated.
- It supports undo and redo.
- It has stable references.
- It has clear errors and recovery behavior.
- It is represented in documentation.
- It has unit and integration tests.
- It has an editor end-to-end test if editor-facing.
- It has performance expectations if performance-sensitive.
- It works in embedded preview and exported runtime.
- It is covered by the declared platform matrix.
- It has an ownership and deprecation policy.
- It is included in release notes and release evidence.

A panel with controls but without these properties is not considered a completed engine feature.


# 12. Final Product Recommendation

Nova_A should not compete by presenting every possible subsystem at once. It should compete by being a focused, dependable 2D engine with a coherent editing model, strong physics, a productive Rhai workflow, modern UI and tilemap tools, transparent packages, and unusually strong release discipline.

The existing 3.0.0 interface already communicates ambition. The 3.1.0-to-4.0.0 plan must convert that ambition into trust. Trust comes from four outcomes:

1. The user does not lose work.
2. The project remains understandable and versionable as it grows.
3. Errors are inspectable and fixable.
4. The same tagged project can be built and validated repeatedly.

If the team follows the roadmap order, version 4.0.0 can be a credible production baseline. If the team continues adding visible modules before establishing project integrity, debugging, import, migration, and release automation, the editor will become broader but harder to finish.

# Appendix B — Recommended Stability Labels
