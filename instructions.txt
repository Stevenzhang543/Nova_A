Yes. After looking at the screenshots and re-reading the actual v1.1.2 source, I would change the roadmap substantially from my previous answer.

Nova_A should not try to become a game engine by simply attaching audio, scripting and animation to the current Entity class. The current architecture is appropriate for a physics/editor application, but if you keep extending it directly, you will eventually end up with one enormous object type containing physics, graphics, audio, scripts, animation, UI and gameplay state.

There are already some clear architectural warning signs:

Entity.ts currently owns transform, texture/color, velocity, mass, gravity, forces, friction, body type and collision diagnostics at the same time.
WorldCanvas.vue currently handles the animation loop, physics stepping, editor input, hit testing, camera interaction and actual Canvas2D rendering in one component.
World.ts rebuilds large Float64Arrays from the TypeScript objects every physics update, sends them into WASM and reads the values back afterward.
Your Rust physics engine is still essentially one very large lib.rs; it is already almost 3,000 lines and contains math, shapes, bodies, collision detection, solver logic and WASM-facing functionality together.
Rendering is currently Canvas2D.

None of these are bad decisions for Nova_A 1.1.2. They are precisely the kind of architecture that lets you get a physics program working quickly. But 1.2.x is the point where I would stop adding random user-facing features and build a foundation that will survive Nova_A 2.0.

Below is the roadmap I would give your coder.

Nova_A 1.2 → 2.0 engineering plan

2. Replace the current per-frame physics ABI

This is a major change.

Currently TypeScript does approximately:

Entity objects
   ↓
build Float64Array
   ↓
WASM
   ↓
reconstruct physics bodies
   ↓
simulate
   ↓
return Float64Array
   ↓
write everything into Entity objects

That is visible in World.ts.

It worked well for a physics editor.

It should not remain the final engine architecture.

Instead create a persistent Rust physics world.

Something conceptually like:

pub struct PhysicsWorld {
    bodies: ...,
    colliders: ...,
    joints: ...,
    contacts: ...,
}

Expose commands such as:

create_body()
destroy_body()

create_collider()
destroy_collider()

set_transform()
set_velocity()
set_body_type()
set_material()

apply_force()
apply_impulse()

step()

get_body_states()
drain_events()

The important change is this:

Before

Every frame:

"Here are all the objects. Rebuild the physics world."

After

When a user creates an object:

"Create body #384."

When the user changes mass:

"Change body #384 mass."

Every frame:

"Advance the already-existing world by 1/60 second."

That is much cleaner.

3. Keep a compact state buffer

Do not replace the Float64 buffer with thousands of JavaScript objects returned through WASM every frame.

Keep a high-performance buffer for runtime state.

For example:

BodyState:

id
position.x
position.y
rotation
velocity.x
velocity.y
angularVelocity
sleeping

Reuse the same allocated buffer where possible.

Do not allocate a brand-new enormous buffer for every object every frame unless necessary.

Configuration changes go through commands.

Runtime transforms come back through the state buffer.

4. Implement a proper fixed timestep

Your viewport currently derives dt directly from requestAnimationFrame and calls the physics world from that loop.

Replace that with an accumulator.

Default:

Physics frequency = 60 Hz
fixedDeltaTime = 1 / 60

Conceptually:

frameDelta = currentTime - previousTime

accumulator += frameDelta

while accumulator >= fixedDeltaTime:
    fixedUpdate()
    physics.step(fixedDeltaTime)
    accumulator -= fixedDeltaTime

alpha = accumulator / fixedDeltaTime

render(interpolatedTransform(alpha))

This gives you:

60 Hz physics
144 Hz rendering

without physics behaving differently at different monitor refresh rates.

Add settings:

Physics Tick Rate: 30 / 60 / 120 / Custom
Maximum catch-up steps
Time scale
Paused

Your single .exe question

This part deserves a very clear answer.

No, modularizing the engine does NOT mean you need DLL files.

This is a common misconception.

You can have:

nova_math
nova_physics
nova_runtime
nova_format
nova_script

as completely separate Rust crates internally and still compile them into:

Nova_A.exe

Cargo crates are source/build modules.

They do not automatically mean Windows DLLs.

For your internal Rust libraries, use normal Rust libraries/rlib where appropriate. The final application links them together.

Your existing Tauri crate already declares several library output forms including staticlib, cdylib and rlib, while nova_core currently builds a cdylib/rlib because it needs a WASM-facing library.

So tell the coder:

Modularize source code aggressively. Do not modularize deployment into DLLs unless there is an actual runtime reason.

Those are completely different things.

Rules I would give the coder

These matter enough that I would literally put them in CONTRIBUTING.md.

Rule 1 — Preserve old projects

Every schema change needs a migration.

Never simply say:

"1.1 projects are incompatible."

Rule 2 — Editor and runtime are separate

Never put game-only behavior inside Vue components.

Never put editor selection logic inside nova_runtime.

Rule 3 — Physics and rendering are separate

A collider does not automatically equal the visible sprite.

A SpriteRenderer does not automatically mean a collider exists.

Rule 4 — Rendering and collision layers are separate

Never reuse one layer property for both.

Rule 5 — No new giant source files

As a guideline:

If a file starts approaching several hundred lines because it has multiple independent responsibilities, split it.

Not because "large files are bad", but because something like the current WorldCanvas.vue is simultaneously becoming an editor controller, renderer, input system and runtime loop.

Rule 6 — Every feature receives tests

Example:

When implementing parenting:

✓ child follows parent
✓ nested child follows grandparent
✓ world/local transforms correct
✓ deleting parent behaves correctly
✓ cycles rejected
✓ save/load preserves hierarchy

When implementing prefabs:

✓ instantiate
✓ override property

Rule 7 — No UI-only implementation

When adding a checkbox such as:

Continuous Collision

do not merely make it save.

Tests must prove it changes the runtime.

Your v1.1.2 README already has a strong emphasis on the chain from UI values → Float64 ABI → physics behavior. Preserve that discipline.

Rule 8 — No silent failure

Invalid project:

show meaningful error

Missing asset:

show missing-asset placeholder
log GUID/path

Broken script:

disable script instance
show line number
continue game if possible

Never crash the entire editor because one asset is malformed.

One particularly important design change

There is one thing I would tell your coder not to misunderstand:

Do not "rewrite Nova_A."

Evolve it.

The sequence should be:

1.1.2 implementation
        │
        ├── create new architecture
        │
        ├── adapt old Entity → new Components
        │
        ├── adapt old Connection → Rope/Joint
        │
        ├── keep old loader
        │
        └── delete old path only after parity tests

Not:

delete everything
↓
write new engine
↓
discover six months later that ropes,
collisions and project loading are broken

The existing physics engine already has working features worth preserving: dynamic/static/kinematic bodies, GJK/EPA-style convex collision machinery, friction/restitution, mass/inertia, sensors, rope simulation, rope collision/breaking and bindings.

Build the game engine around that work, then refactor the internals behind tests.

Nova_A 1.2.0 objective: create a permanent modular runtime foundation while achieving 100% behavioral compatibility with Nova_A 1.1.2. Do not add major gameplay systems. Split the Rust core, introduce a persistent PhysicsWorld, implement fixed-timestep simulation, introduce versioned serialization and persistent UUIDs, preserve all existing UI/physics behavior, and keep the Windows editor distributable as one clean application. No old project may stop working.

Then 1.3.0 is where the visible transformation starts.

That ordering is important. If you jump directly from the UI in your screenshots into scripts, sprites, tilemaps and audio, you'll be building them on top of an Entity class and WorldCanvas.vue architecture that was never designed to hold an entire game engine.

With this sequence, 1.2–1.4 transforms Nova_A's architecture, 1.5–1.8 transforms its capabilities, 1.9 transforms it into something that can ship games, and 2.0 formalizes it as a real engine.
